Healthcare Quality Lab V6.12 Engineering Report

November 18, 2026 · Standalone project: /Users/erdalkilic/Documents/Healthcare Quality Lab

Why we built this version

A model comparison is difficult to trust when the prompt, scenario, runtime or definition of success changes between runs. V6.12 freezes those choices and saves the original answers, including errors. The purpose is to learn from bounded experiments, not to declare that one model is universally better or hide assistance inside an accuracy score.

What we built and where

healthcare_quality/experiment_lab.py defines a strict experiment configuration, protocol capture, exposure history, durable trial checkpoints, cancellation and per-group metrics. experiment_api.py exposes explicit jobs and read-only status. tools.experiments runs local comparisons or exports a retained record without requesting another model answer. The workbench displays model, prompt, mode, eligibility, provider errors, unknown outcomes, latency and token counts. New state uses experiments-v612.sqlite.

Eight new authored input plans are frozen in data/experiment_cohort_v612.json, covering different amounts, coordination, policy periods and plans. The file contains no expected observations. Two tasks are labeled development and six reserved until exposed in the local ledger. First-recorded exposure describes that ledger only; public plans and model training data cannot be proven globally unseen. Existing V6.4 measurements stay separate.

Protocol and truthful controls

The protocol captures the selected models, fixed prompt versions, task IDs, modes, repeat count, installed model digests, provider settings, cohort hash, source/contract fingerprints and prompt hashes. Each AI trial receives fixed actions, actors and business inputs and must fill expectations once. Changing the scenario fails eligibility. It receives no reference-derived expected answers and there is no correction step.

The original baseline prompt and the focused V6.8 prompt are both available. This makes a same-input prompt comparison possible instead of changing prompt and model together and attributing the result to prompting alone. A small local experiment is still illustrative and correlated; it is not a statistically reliable model ranking.

Calculator-control rows deterministically compile the authored frozen plan without a model request. They have a different expectation-author label and ai_reasoning_metric=false. They are not credited as AI accuracy or described as AI-designed plans. Actual AI planning remains measured separately in V6.8, where the first model call produced the scenario itself.

Budgets, interruption and repeatability

Configuration permits only known models, prompt versions, task IDs and modes, with one to three repeats and at most twenty-four total trial rows. The CLI checks that selected models are already installed locally. No model download, arbitrary endpoint, cloud fallback or paid API is added. Local token counts do not imply zero hardware or electricity cost; the report does not invent an API dollar price.

Exposure and a trial's running phase are persisted before inference. Raw responses are saved before assessment. Renewable leases protect active jobs; late completion is fenced. Explicit cancellation preserves completed responses and marks an in-flight outcome unknown. The provider call may still finish in the background, but cannot overwrite the cancelled record. Interrupted outcomes are not counted as provider failures or wrong financial answers. Status polling reads saved jobs; it never starts another inference.

Metrics group results by model, prompt and authorship mode. Provider failures, schema validity, first-attempt eligibility and wrong/incomplete answers remain separate. Repeated stability compares scenario semantics and observations rather than generated titles. Repeats share fixed settings and are correlated, so the dashboard does not treat them as independent samples.

How we tested it and what we achieved

Controls cover authorship separation, exact call counts, reserved exposure across reruns, invalid configurations, budget limits, provider timeouts, interruption, cancellation with a late response and semantic repeat stability. The browser runs a zero-call calculator control and verifies the result is labeled separately from reasoning. Core regression uses offline providers; actual local model experiments are retained separately below.

We now have a reproducible way to compare prompt and model behavior while keeping the practical calculator-backed path available. The actual selected matrix, raw answers, installed digests, observed runtime and success/failure counts—not a polished summary alone—are the evidence. V7.0 will package this connected workflow with fresh-start demonstrations, final cross-browser checks, architecture material and release receipts.
