Healthcare Quality Lab V5.5 Engineering Report

What we built and why

V5.5 adds a test coverage dashboard, local AI gap analysis, deterministic duplicate detection and observed defect-detection scoring. V5.4 established stronger expected-value checks. This release asks a different question: does a reviewed test add a missing scenario, and what faulty behavior can it actually detect?

A growing test count can conceal repeated scenarios, incomplete assertions and surviving defects. V5.5 makes those distinctions visible. A rule citation is treated as a link, not proof of complete coverage. An AI suggestion is not a test. A valid expected value is not evidence that a test detects every relevant defect. An infrastructure failure is not credited as a detected product fault.

The complete final deterministic suite passed 549/549 tests, with zero failures and zero skips: 446 unit, 65 API and 38 Chromium browser tests. All seven retained evaluator and five workflow defect seeds were detected by the established benchmark tests. This is 78 more deterministic tests than V5.4.

In the separate real Ollama demonstration, one gap-analysis request led to two targeted generated cases. Both passed structural, assertion-completeness, independent-reference and scenario checks without correction. The engineering-reviewed cases closed two of four missing scenarios in the defined map. Their healthy baseline passed, but the selected two-case suite detected only 2/12 action-family-applicable fault profiles. Ten survived. That result is preserved and explained rather than presented as broad AI test effectiveness.

What the coverage dashboard measures

The baseline inventory contains the 28 existing authored golden evaluator examples plus four explicit workflow cases for ownership, duplicate rejection/readback, approval ordering and payment/history. Those cases use authored expected values. They are not relabeled as AI output and are not filled from the application under test. Automated tests verify all 32 against the independent reference, assertion policy and healthy application runner.

The dashboard also scans the latest 100 saved Studio experiments. It shows unreviewed and stale cases for inspection and duplicate analysis, but they cannot close gaps. AI cases become eligible only if current approval hashes, contract, assertion policy, completeness and reference checks all pass. Editing a case or invalidating its approval removes current coverage credit on refresh.

The rule map links 13 written HC/WF rules to cases, shows eligible cases, identifies missing defined scenarios and displays current observed fault detections. Historical fault evidence loses current-map credit if implementation fingerprints or approval snapshots change. The original evidence remains downloadable as history.

This is a deliberately bounded mapped inventory. It does not discover every pytest test, measure executed Python lines or branches, enumerate every plan/service/flag combination, or certify all clauses of a rule. Existing pytest input-validation and concurrency tests may exist outside this catalog. A scenario labeled missing means missing from the eligible mapped case inventory, not necessarily absent from the whole repository.

WF-006 is especially explicit: sequential declarative cases cannot establish concurrent duplicate behavior, database reopen persistence or rollback under storage faults. The dashboard labels that limitation instead of showing a misleading complete badge. The existing authored tests continue to exercise those concerns separately.

The eleven defined scenario checks cover invalid zero amounts; inactive/uncovered precedence; network/authorization precedence; formulary denial; deductible-plus-one; cap-plus-one; foreign-customer ownership; duplicate rejection with readback; skipping approval with unchanged readback; zero payment with post-payment evidence; and paid replay with unchanged ledger/history.

At the start of the isolated demonstration, four were missing: invalid-zero, cap-plus-one, zero-payment and payment-replay. After the two reviewed generated cases, cap-plus-one and zero-payment were represented. Invalid-zero and payment-replay remained missing. No model wording or mere target-gap metadata could close a scenario by itself.

How duplicate detection works

Duplicate detection is deterministic and ignores case titles, case identifiers, rationale and other prose. It normalizes omitted true defaults and valid claim-ID renaming while preserving action order, actor identities, input amounts and relationships among claim references. Renaming one claim consistently is different from changing a later step to refer to another claim.

Invalid claim identifiers retain their literal boundary behavior. A one-character invalid identifier cannot be normalized into the same scenario as a valid ID. Otherwise, a negative validation test could be incorrectly collapsed into a positive workflow test. A dedicated regression protects this distinction.

Equivalent input scenarios are grouped, then their assertion sets are compared separately. Matching inputs and matching expectations are equivalent-assertion duplicates. Matching inputs with an extra payout, reason, payment or history assertion remain distinct assertion sets. Conflicting overlapping expected values are flagged explicitly. The feature never deletes a case, changes an approval or treats wording similarity as behavioral equivalence.

Scoring evaluates exact scenario/assertion equivalents once. It retains different assertion sets, including stronger observations. Raw mapped-case counts and unique scenario/assertion counts are shown separately, so duplicate records cannot inflate the unique-test metric or defect numerator.

The portable duplicate probe deliberately renames a copy of an actual generated case to demonstrate grouping. It is labeled a constructed probe, not another AI generation or additional coverage achievement. Earlier proposals and their mistakes remain available for inspection.

How AI gap analysis and targeted generation work

Clicking Analyze gaps with Ollama makes one explicit local request. The server freezes the current mapped dashboard, missing-gap identifiers, written rules, implementation fingerprints and latest available scoring context. The model may return one to three distinct suggestions from the supplied missing-gap IDs. Each includes an explanation and testing brief. Unknown IDs, duplicate suggestions, malformed JSON and provider failures are saved as failures with available raw evidence.

The model does not determine that a gap is closed. That decision remains a deterministic scenario check over eligible cases. Suggestions cannot execute tests or grant approval. A separate button explicitly requests an unapproved Studio proposal for one selected suggestion. The server supplies the frozen scenario criteria and authoritative rule IDs; the model's brief remains untrusted task data.

The resulting experiment retains its analysis ID, target gap and dashboard snapshot hash. Studio performs the existing structural, expected-value and completeness checks. The user must inspect and review the case before execution or scoring. If a model ignores the requested scenario, its lineage alone does not earn coverage credit. Generation from an implementation-stale analysis is blocked; old analyses remain historical evidence.

The analysis uses the existing local model allowlist and shared model semaphore. Its persistent lease and heartbeat support interruption recovery and fenced completion. An expired worker cannot later mark its result successful. The scoring jobs use the same persisted-operation mechanisms in their own store. Cases, prompts, raw responses, snapshots and errors are preserved; nothing silently substitutes an offline fixture for a failed live request.

How defect-detection scoring works

The scoring endpoint accepts at most four reviewed experiments and at most four approved cases in total. It rejects missing review, wrong revisions, stale contracts, changed case hashes, incomplete assertions and reference disagreement. It freezes the exact approved cases, their origins, approval snapshots and implementation fingerprints before execution. Interactive claim databases are not used.

Every unique selected case first runs against healthy services in a fresh temporary database. If any healthy baseline fails, no numeric mutant score is produced. This prevents a broken test from receiving credit merely because it also fails against faulty code.

The scorer then runs the selected cases against twelve fixed authored fault profiles: eligibility, uncovered-service acceptance, network bypass, authorization bypass, formulary bypass, skipped deductible, removed cap, ownership bypass, duplicate replay, skipped approval, doubled ledger amount and skipped history. These are internal test profiles. Public claim evaluation continues using healthy behavior; the scoring endpoint cannot supply arbitrary code or an arbitrary fault name.

Applicability is defined by action family. Evaluator profiles apply to cases containing evaluate actions; workflow profiles apply to workflow actions. This is a broad denominator, not a claim that each particular input activates every profile. Nonactivated defects survive. Families absent from the suite are labeled not applicable rather than silently credited. There are no seeded input-validation or WF-006 concurrency profiles in this measurement.

Only an actual expected-versus-observed assertion mismatch counts as a detection. Results identify the case, step, field, expected value, observed value and associated fault-rule mapping, with full runner evidence behind them. Surviving faults are retained. Execution errors are labeled errors and suppress a numeric score instead of increasing the detection count. Unknown profiles are rejected. The budget is four cases, twelve profiles and at most 52 case runs, with a 30-second soft check between mutant runs and existing runner action/time bounds.

The displayed numeric score is detected profiles divided by applicable profiles when there are no errors. A profile detected by multiple cases counts once in the suite numerator. This is an observed score for known authored seeds, not an exhaustive mutation score, independent product oracle or general AI-quality rating.

The real demonstration used the installed qwen2.5-coder:3b through loopback Ollama. One analysis request produced grounded suggestions; two further explicit generation requests created the selected cases. Neither case required AI correction or reference-assisted replacement. Engineering reviews were explicitly labeled automated local attestations, not authenticated human approvals. The product itself did not automatically approve the model's proposals. The opt-in measurement operator checked their inputs, assertions, reference result and target predicate before initiating scoring.

Both healthy baseline cases passed. The cap-boundary case detected the removed-limit fault. The workflow case detected skipped history. The suite result was 2 detected / 12 applicable profiles, or 16.67%, with zero execution errors. Ten profiles survived: eligibility, coverage, network, authorization, formulary, deductible, ownership, duplicate replay, approval skipping and doubled ledger amount.

Those survivors are informative. The cap-boundary case cannot detect a skipped deductible when both healthy and faulty calculations still reach the cap. The zero-payment case cannot detect doubling the ledger amount because two times zero is still zero. A positive-payment scenario is needed for that specific fault. Ownership, replay and ordering faults also require actions that these two cases do not perform. Correct assertions and two newly closed gaps therefore did not imply broad defect detection.

This selected AI-suite score must not be confused with the retained framework benchmark, whose different authored tests detect all twelve seeds. The new scorer's targeted unit tests also demonstrate each supported profile is detectable by a suitable reviewed case. These are separate populations and claims.

All three actual model requests, prompts, model identity/digest, generated proposals, reviews, frozen analysis and runner evidence are retained. After final predicate/boundary hardening, the same reviewed cases were rescored against final source without new model calls. Earlier score records were preserved. The measurements are small development demonstrations on known written rules, not blind holdouts or general reasoning benchmarks.

How to use the finished framework

Open http://127.0.0.1:8895/#test-coverage. Review eligible versus raw case counts, the rule map, remaining scenario gaps and duplicate groups. Inspect saved scoring evidence to see both detected and surviving faults; a healthy baseline pass is recorded separately.

To extend coverage, explicitly analyze the current gaps with Ollama, inspect a suggestion and select generation of an unapproved proposal. In Studio, verify the scenario, required assertions and reference calculation; use the existing bounded correction or confirmed reference assistance if needed. Select cases, attest to review and save approval. Return to the coverage dashboard, refresh, select the approved experiment snapshots and measure defect detection. Changing a proposal requires fresh approval; old results remain historical.

The result is a working loop from a defined gap to an AI proposal, verified expectations, reviewed execution and observed test value. We now have tools to explain why a test adds coverage, why two tests overlap and why a passing test can still miss a defect. Shared synthetic facts, fixed gap predicates, a bounded inventory and known fault seeds remain practical limits. Nothing here establishes real Medicare/commercial benefit correctness, clinical suitability or compliance certification.
