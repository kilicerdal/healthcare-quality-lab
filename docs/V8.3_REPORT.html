Healthcare Quality Lab V8.3 Engineering Report

What we built and why

V8.3 makes the experimental AI workbench easier to operate, clearer to present and safer to stop. It adds more precise worksheet instructions, honest partial-run metrics, explicit time budgets, correct self-review analysis and a persistent replay-first showcase launcher. It does not establish improved model accuracy.

The project remains the standalone repository at /Users/erdalkilic/Documents/Healthcare Quality Lab. It is separate from the user's other frameworks. No VS Code session was opened. All claims, benefits, identities, ledger entries and payments in this lab are synthetic; these tests demonstrate software engineering rather than actual Medicare or commercial-policy compliance.

The practical problem was that a good engineering framework still had three presentation and operation weaknesses: an interrupted experiment could look like a finished score, live model work could take longer than the user intended, and a previously running showcase could be unavailable. The AI also still confused rejected coverage with member responsibility and confused policy limits with the remaining balance before each line. This version addresses those specific weaknesses without a large benchmark or another broad feature expansion.

Understanding the original evidence

The saved V8.2 qualification planned twenty trials. Only seven were assessed before interruption. All seven assessed predictions had correct API observations; four also had correct numeric worksheets, while three failed worksheet checks. Thirteen trials were not assessed, including an interrupted request whose eventual outcome is unknown. These are different measures and should not be collapsed into a final accuracy percentage.

V8.3 displays those counts directly: seven assessed of twenty planned, seven correct API expectations, four fully valid predictions, three worksheet mismatches and thirteen not assessed. It marks the experiment INCOMPLETE and suppresses its final percentage. The original record, model output and source identity are unchanged. Historical records do not become current-source export candidates merely because a new interface can display them.

The six faults that survived the earlier AI coverage remain an AI coverage limitation. V8.2 already contained human-authored witnesses detecting all six, contributing to its authored 27/27 pricing mutation result. V8.3 does not award that authored coverage to the AI, or claim its prompt changes closed those gaps.

Worksheet guidance without calculator assistance

The new healthcare_quality/compact_expectations_v83.py protocol retains immutable server-owned inputs, model-authored answers and the existing independent evaluator. It adds two generic rules to the prompt.

For rejected coverage, eligible money belongs in noncovered money. It is not an initial member charge. The relevant member, capped-member, payer and payout worksheet amounts remain zero. The model must still calculate and supply the other required fields correctly.

For a multi-line claim, remaining caps describe the account immediately before that particular line. Earlier covered lines update account usage before a later line is assessed. A rejected line must not reset the remaining balance to policy limits.

The V8.3 cohort retains the fourteen V8.2 tasks and adds two explicitly exposed development examples: D83-01 for rejected vision coverage and D83-02 for mixed-line balance timing. Previously published H82 tasks are labeled historical rather than reserved. These sixteen tasks are not a new blind qualification set.

Prompt construction does not consult the calculator or fill expected values. Parsing preserves model-authored numeric aliases. The independent evaluator checks frozen answers afterward; it does not correct them. Regression tests deliberately replace pricing/oracle access during prompt construction and verify that the original three bad worksheets still fail with their values unchanged.

Bounded live jobs and useful estimates

The browser, V8.3 API and current compact CLI now accept a total job budget of 1–300 seconds, defaulting to 180 seconds. Invalid values, booleans and out-of-range numbers are rejected. The budget begins when the job is admitted after model-availability preflight; preflight is separate and bounded. It is not a promise that the entire request, including preflight, finishes in exactly that interval.

A timer marks an over-budget job interrupted, records the reason, marks an active call interrupted and preserves pending rows. Per-request transport timeouts are clipped to the remaining job budget without changing the shared provider configuration. A synchronous caller can return at the budget even when a provider ignores cancellation. Persisted deadlines also apply during recovery.

Backend cancellation is best effort. A running Ollama operation may continue after the visible job stops; the generation lock remains held until its worker returns. Late output cannot overwrite the stopped record. This avoids both a misleading completed result and overlapping work against the same provider. It does not claim instant termination of backend computation. Existing older research entrypoints retain their original settings; the bounded defaults apply to the current compact path.

The estimate endpoint makes no generation call. It calculates the number of requests, including optional review and stepwise generation, and uses historical completed-response medians for each model when available. Explicit fallbacks are used otherwise: ninety seconds for a 27B model and fifteen seconds for smaller models. The estimate includes its basis and whether the selection is likely to fit the budget. It is planning information, not a latency guarantee or proof of timeout improvement.

Experiments with different total time budgets cannot be pooled into one comparable aggregate. The budget, deadline and clipped timeout are retained as evidence.

Correct analysis of optional self-review

The report analyzer previously treated the absence of a self-review answer as if a requested review had made a correct first answer wrong. That manufactured a regression when review had never been requested.

V8.3 compares first and review stages only when review was requested and both stages were assessed. Otherwise it reports review_not_requested or review_unassessed. Applying the analyzer to the actual V8.2 record produces twenty unrequested-review entries and no fabricated review regressions. No new model request is needed for this correction.

Replay-first dashboard and reliable startup

Opening the workbench loads saved evidence through read-only requests. Optional live inference is collapsed by default. A user must expand it, select a scenario, choose a budget and request a duration estimate before Start becomes available. Changing any selection invalidates the estimate. Interrupted calls are labeled outcome unknown; later pending rows are labeled not run.

Hosted Firefox and WebKit testing found a real startup race: the estimate button could be clicked before its scenario configuration finished loading. Those earlier runs were not passing acceptance. The corrected interface disables Estimate until configuration is ready. It also ignores a delayed estimate response if the user has changed the selection or budget in the meantime. Two deterministic browser regressions hold those responses to verify both cases. The fix changes control readiness rather than increasing test waits.

The new tools/showcase_server.py provides start, status and stop. It waits for readiness, retains SQLite state, seeds the original interrupted replay only once and starts no model inference. Repeated start reuses a healthy owned server. Stop checks a token-backed ownership endpoint and never kills an unrelated process based on a PID file. Existing shared-authentication settings are honored; local launcher credentials are stored privately rather than committed.

.venv/bin/python -m tools.showcase_server start
.venv/bin/python -m tools.showcase_server status
.venv/bin/python -m tools.showcase_server stop

The default address is http://127.0.0.1:8902/#workbench. State is in .local/demo-v830. The operating guide explains first-time dependencies, replay, estimates, budgets and intentional inference. No dependency or model download occurs automatically.

Actual live pilot: a failure retained honestly

Exactly one new live request was made: qwen2.5-coder:3b, exposed development task D83-01, a thirty-second total budget, no self-review and no retry. The response took 11,967.05 milliseconds; the command finished in approximately 12.27 seconds.

The pilot was schema-valid but failed both API observations and numeric worksheets: zero of one predictions were eligible. Although one rejected-line member field was zero, other worksheet fields were wrong, some used-account fields copied limits, and lifecycle/ledger expectations were incorrect. The export gate returned HTTP 409 EXPECTATIONS_BLOCKED. No values were repaired, approved or executed as a passing AI case.

This pilot ran on the initial V8.3 source fingerprint b9ea5cb40807f310dc4cfaba12488f4d398d4ea2c43f0750dcf70be018ec133b, before the final browser-readiness fix. That later fix changes HTML, JavaScript and browser tests; it does not change the prompt, parser or evaluator. The pilot is still evidence from that earlier source, not a new final-source benchmark. No second pilot was run merely to seek a better answer.

The result does not demonstrate improved AI accuracy, qualification or timeout rates. It demonstrates that one bounded actual model response was retained and rejected by independent checks. The deterministic tests establish the new timeout behavior; one live response cannot establish a general latency improvement.

What we achieved and what remains

The showcase now explains partial evidence accurately, opens a recorded example without inference and has a state-preserving launcher. Live jobs have explicit admission-time budgets, durable interruption records and late-result protection. Optional review analysis no longer manufactures regressions. The worksheet prompt is more precise, and the failed real pilot remains visibly blocked.

The framework is ready to present as an AI-assisted quality-engineering research showcase with independent validation. Autonomous model-authored expected values remain experimental. The next AI research step would require a separately planned, time-bounded evaluation on fresh inputs with strict first-attempt scoring. That evaluation was deliberately not added to this focused version. This is an honest engineering improvement, not a claim that the model is flawless.
