# Learning walkthrough: what each tool contributes

## Start with the story

A test that passes is only one piece of evidence. In this lab, ask four questions separately:

1. Did the AI author correct expected values before seeing any reference answer?
2. Do the application's and reference calculator's results agree with the written synthetic rules?
3. Does the journey preserve balances, ledger entries and history across multiple operations?
4. Can the test detect a controlled defect?

## Follow one model attempt

Open `artifacts/v8.7/study/plan.json` and find a task. It contains input facts and the declared model/time/call limits, not expected answers. Open that task's `-r1.json` raw record. Its protocol identifies the model digest, settings and tested source hash.

The first call asks Ollama for pricing and worksheets. The second asks for lifecycle and ledger predictions using the model's own unverified quotes. In each `rows[].calls[]`, read the exact `prompt`, `generation_schema`, frozen `response`, phase and timings. This is actual local model evidence. Tests under `tests/support/` use offline doubles and must not be presented as real model performance.

Only after the responses are frozen does the independent evaluator compare them. `rows[].first.assessment` distinguishes schema validity, observation correctness, worksheet correctness and export eligibility. No reference number is substituted into the model's answer.

A repeat is another original call pair on an already exposed input. It measures consistency, not fresh-case accuracy. The two preselected repeats are reported separately.

## Read the rule-review examples

In `healthcare_quality/rule_review.py`, the expected literals were written from the synthetic contracts. Work through one manually. For 11002 cents under H1, subtract the 10000 deductible and 1000 copay; floor 80% of the remaining 2 cents to 1 cent payer. The member pays 11001 cents. Both calculators must match those fixed literals.

An independent person can use `docs/V8.7_RULE_REVIEW_CHECKLIST.md` to review the assumptions. Automated success does not fill in that person's sign-off.

## Understand defect scoring

The trusted mutation catalog changes arithmetic or min/max expressions in project-owned pricing code. Before mutation scoring, every case must pass the healthy baseline and independent reference gate. An eligible original AI test earns detection credit only when a mutation makes its assertions fail. Reference-authored journeys receive their own score.

A surviving mutant needs investigation: it could expose a test gap or be equivalent on the valid input domain. A score is not a promise to catch all possible bugs.

## Tools and roles

| Tool | Role | What the evidence proves |
| --- | --- | --- |
| Ollama / qwen3.5:27b | Local expected-value author | Actual frozen predictions on declared inputs |
| Coding assistant | Implementation and engineering explanation | Code changes; not an independent human review |
| Python / pytest | Unit, API and harness verification | Repeatable automated assertions |
| Playwright | Browser behavior and responsive layout | Real user-flow checks on tested browsers |
| GitHub Actions | Hosted deterministic acceptance | Checks passed on a specific source commit |
| Fraction reference + fixed vectors | Independent arithmetic checking and rule review aid | Agreement with the bounded synthetic contracts |
| Trusted AST mutations | Deliberate defect-detection experiment | Which named mutations each suite caught |
| Git / SHA256 | Version and evidence traceability | Detectable content/source changes; not human approval |

Adding Copilot, ChatGPT or Claude as another reviewer should have a bounded role and its own recorded outcomes. This version makes no unperformed claims about those tools and introduces no cloud API charge.
