## 3. Why a passing V5 suite did not settle these questions

V5's 325 passing tests demonstrated the behavior they asserted. They did not include the exact cached-bytecode import case or persistent Studio state after a worker was killed. The retrieval test only checked that the requested rule ranked first, which allowed unrelated second and third results to go unnoticed.

I first converted the review findings into eight regression reproductions. One creates a harmless source module with a matching but different cached bytecode value. Two preserve legacy busy records and instantiate a fresh service. Five exercise exact, lowercase, multiple, unknown and extended rule IDs. All eight failed before implementation.

This matters because a correction needs evidence that the old behavior is detected. Merely increasing a test count, checking a function exists, or expecting a new implementation detail would not establish that these reported defects were fixed.

## 4. Release-cache defect: cause and consequence

V5's verify_tree deliberately ignored files inside __pycache__. Python can read a matching compiled cache even with -B or PYTHONDONTWRITEBYTECODE set. Those settings prevent cache writes; they do not make an existing cache impossible to import.

The reproduction stages a source file whose value is good, briefly compiles a same-size temporary version whose value is evil, then restores the original source bytes and timestamp. The source digest again matches the manifest. Under V5 verification, the tree passed while the interpreter imported the cached value. The words are just harmless strings; no application source, patient data or real system command is involved.

The consequence is narrower than a remote compromise claim: someone able to place a cache in a staged payload could make the staged verification result disagree with the application code actually imported. That violated the release check's own consistency promise.

## 5. Release-cache correction

V5.1 rejects __pycache__ paths and .pyc/.pyo files in archive member validation, even if someone lists their digests in the manifest. The source-package builder excludes compiled artifacts, and staged-tree verification now rejects cache directories and bytecode instead of silently ignoring them. Even an empty unexpected cache directory is rejected.

The serve and activate paths already call staged verification, so the corrected check also blocks activation and startup of a cached payload. The reproduction now expects ReleaseError rather than allowing a staged verification success. Existing source-digest, traversal, symlink, duplicate-entry and package-budget checks remain in place.

The release launcher also removes inherited PYTHONPYCACHEPREFIX, PYTHONPATH and PYTHONHOME values before starting its fixed child interpreter. It retains PYTHONDONTWRITEBYTECODE=1 so normal staged application imports do not create new caches. A separate launcher test proves the external cache/import settings are not inherited.

Rejecting an unexpected cache is intentional. The tool does not silently delete files from a payload or try to repair an installed release. Restage the trusted clean archive into a clean deployment directory after inspecting the rejection. Existing states remain outside the immutable payload.

This is file/import consistency checking for the local release workflow. It is not a signed publisher identity, verification of every installed third-party dependency, or a guarantee against a privileged writer changing the filesystem after verification. Those broader boundaries remain unchanged.

## 6. Interrupted AI jobs: original failure

V5 persisted generating before making the provider call and running before executing reviewed cases. If its process died before saving completion, those states survived in SQLite. A fresh StudioService instance did not reconcile them. Editing, reviewing or executing then returned EXPERIMENT_BUSY indefinitely.

Simply setting every busy record back to proposed on startup would be unsafe. A second service instance could be observing a genuinely active operation. An old worker might return later and overwrite recovered state. An interrupted execution might also have lost its completion evidence, so treating it as successful or retaining its executable approval would be misleading.

The V5.1 design therefore separates three questions: who currently owns an operation; when ownership expires; and what a recovered record is permitted to do next.

## 7. Persistent leases, heartbeat and fenced completion

The existing SQLite experiment store gains a studio_operations table. Each active Studio generation or execution has a unique token, operation kind, start time, last heartbeat and expiry. The default lease lasts 30 seconds, renewed every five seconds while the worker remains active. Tests use shorter explicit timings to exercise expiry without waiting thirty seconds repeatedly.

Record creation and lease acquisition commit in the same transaction. For execution, the approved case/approval snapshot and pending run ID are also saved before the runner starts. A heartbeat updates the separate operation row, so it does not repeatedly rewrite or race against the large JSON experiment record.

The heartbeat covers the entire generation operation, including returned-output validation and completion, as well as execution. One regression deliberately holds validation longer than the initial short test lease and confirms a second service still sees a live operation. A normal successful or failed completion removes the lease and stops its heartbeat thread.

Before accepting results, the worker must still hold the matching unexpired token. A worker whose lease has expired or been recovered receives OPERATION_LOST. It cannot replace a recovered record, restore old approval, or append a late passing result. A test recovers execution, records a fresh review, then releases the old worker and proves that the old result does not overwrite the newer revision.

These tokens are ownership/fencing identifiers, not user authentication. The implementation remains local SQLite coordination, not a distributed task service or exactly-once external payment protocol.

## 8. Recovery behavior and evidence preservation

Recovery runs when a Studio service starts and when experiments are read/listed or changed. If a lease remains valid, the record stays busy. Once an operation lease expires, recovery marks its record interrupted, advances its revision, records the reason and invalidates approval and approved case IDs.

Existing raw generation, proposed case data, completed runs and history are preserved. Previous approval and operation metadata are saved in the interruption history event. For new interrupted executions, the pre-saved pending run becomes an interrupted run with its approved case snapshot and an explicit unknown-outcome message. No passing result or observed assertion is invented.

Recovery commits independently of a rejected stale mutation. This prevents a subsequent STALE_REVISION or REVIEW_REQUIRED response from rolling back the recovery itself. Tests cover this transaction boundary and repeated reconciliation without duplicate interruption events.

An interruption is recognized on a subsequent startup/read/list/mutation after lease expiry; there is no new always-running recovery scheduler. Clock changes, long database stalls or loss of heartbeats can conservatively interrupt an operation. Fencing prevents an expired worker from silently committing afterward.

## 9. Explicit retry and mandatory re-review

An interrupted generation can be retried through POST /api/ai/experiments/<id>/retry or the new Studio button. The request requires the expected parent revision, reviewer label and note. It creates a new experiment with retry_of pointing to the original. The parent records the requested child ID in its history, and its revision advances atomically with child creation.

The original experiment is preserved. The new generation returns unapproved proposals, with no execution or inherited approval. Concurrent requests using the same parent revision create only one child; the other request is rejected as stale. A retry may still fail normally if the local provider is unavailable, and that failure remains explicit.

Interrupted execution deliberately has no generation-style replay button. The UI explains that the outcome is unknown and the prior approval has been invalidated. The reviewer must inspect the preserved data, select cases, attest again and save a fresh review before another execution. Old approved pytest export is blocked after interruption as well.

The browser tests exercise both paths through a real HTTP server: retry creates a different unapproved child, and interrupted execution remains disabled until a new review is saved. The UI also avoids displaying an interrupted run as zero failed cases implying success; it explicitly labels the outcome unknown.

## 10. Upgrade behavior for legacy records

V5 records have no operation lease, so their active ownership cannot be inferred using this new table. During the V5.1 upgrade, legacy generating/running Studio records are marked interrupted with a specific legacy-recovery reason. Their data/history are retained and their approval is invalidated. Older records without a pending run cannot acquire a fabricated run ID or outcome.

**Stop older application workers before opening the same stores with V5.1.** A V5 worker does not understand leases or fencing and must not run concurrently against those same databases. Fresh V5.1 service instances can safely observe each other's valid leases; this does not make mixed-version writers safe.

The schema addition is additive. Claims, payments and completed experiments are not reset or replayed. Release rehearsal uses separate per-release state, while an in-place upgrade should be preceded by an ordinary SQLite backup and a stopped older runtime. Source releases continue to exclude mutable databases.

## 11. Retrieval defect and exact-ID correction

The old tokenizer split HC-007 into hc and 007. Other HC contracts shared hc, so they appeared as secondary results even for an exact query. HC-999 and HC-0070 could also produce plausible-looking unrelated matches. The earlier test only required the correct first result.

V5.1 first extracts complete explicit HC/WF identifiers with boundaries and normalizes their case. If a query contains explicit identifiers, only those known identifiers are returned, in request order with duplicates removed and the configured result limit applied. Unknown IDs return no substitute. An extended HC-0070 is not mistaken for HC-007.

Explicit sources are authoritative even when keywords accompany them: WF-004 hospital still selects WF-004 rather than silently adding hospital-related contracts. A mixed query containing known and unknown explicit IDs returns only the known requested IDs. To search more broadly, use a keyword-only query.

Keyword search remains transparent lexical overlap. It removes rule-ID text, namespace tokens and numeric fragments from matching and searches non-ID contract content. It returns actual matched terms with deterministic ordering. New result metadata identifies exact_rule_id versus lexical_overlap and retrieval version exact-ids-lexical-v2. Investigation records save that retrieval version.

Scores rank matches; they are not confidence percentages. The change prevents the reproduced namespace pollution but does not establish that a model's reasoning is semantically supported by its citations. The explanation schema and explicit fact/hypothesis separation remain necessary.

## 13. What was tested and why

The original reproduction tests establish the defects were detected before implementation. Broader release checks reject compiled artifacts listed in a manifest, empty cache directories and inherited external cache/import paths. Existing package validation tests remain active.

Recovery checks cover live generation across another service startup, renewal beyond the original expiry, heartbeat during output validation, expired generation, late completion, preserved execution snapshots, review invalidation, successful cleanup, retry lineage, stale/concurrent retries, recovery surviving rejected mutations and blocked old pytest export.

Two tests launch real worker subprocesses, wait until generation or execution has actually begun, terminate only those children, instantiate a new service and poll until lease expiry/recovery. They prove process-death behavior against persistent SQLite state, not merely a mocked exception in one function. They make no model request and use only synthetic case fixtures.

API tests exercise recovery on read, the new retry endpoint, unapproved child state, stale retries, execution review gating, wrong retry kind and exact/unknown rule lookup. Browser tests verify the corresponding visible controls and messages through headless Chromium. No VS Code or visible browser interaction was used to show work.

The full verifier then ran all 370 collected checks, retained evaluator/workflow fault experiments and source-fingerprint consistency. It records the command, environment, category counts and JUnit results. The final implementation fingerprint must remain unchanged for its result to stay fresh.

## 16. Remaining boundaries and achieved result

V5.1 addresses these three reviewed defects. It does not add a distributed queue, automatic replay, real user authentication, signed supply-chain attestations, a new healthcare benefit model or a new model-quality benchmark. Comparison jobs retain their previously documented local daemon-job behavior; the new leases cover Studio generation/execution.

The existing provider timeout and soft comparison budget remain unchanged. Reference expectations and review remain human/engineering responsibilities. Better retrieval precision does not prove a cited explanation is correct, and passing these finite tests is not Medicare compliance certification.

The concrete improvement is that the release validator now rejects the demonstrated cache bypass, AI experiments can leave abandoned busy states without losing evidence or bypassing approval, and exact source selection no longer introduces unrelated rule fragments. Each correction has an original failing reproduction, broader regression coverage, a documented reason and a bounded operating model.
