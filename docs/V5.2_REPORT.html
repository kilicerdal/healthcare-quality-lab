Healthcare Quality Lab V5.2 Engineering Report

1. What changed and why

V5.2 improves the completeness of AI-created test proposals, particularly payout, payment and history assertions. V5.1 could accept a structurally valid case with only a status and another narrow observation. Missing business assertions were warnings, so a reviewer could approve a test that never checked the financial or audit behavior it purported to cover.

V5.2 adds three layers: an outcome-specific schema requests complete observations from local Ollama; a deterministic per-step assessment identifies missing or unsupported assertions and missing rejection readbacks; and a versioned approval policy blocks incomplete selected cases at review, execution and trusted pytest export.

The important limitation is explicit: complete assertions are not necessarily correct assertions. The fresh live comparison improved field completeness but did not improve overall oracle correctness. Those less flattering results are preserved, explained below and never edited into successes.

Final local verification: 400 passed, zero failed/skipped — 310 unit-category, 57 API and 33 Chromium checks; all 7 evaluator and 5 workflow known faults detected.

Package/rollback rehearsal: passed — actual V5.1/V5.2 startup, claim workflows, rollback and state preservation; candidate v5.2.0-7a1ea4df909b.

3. What completeness means

Completeness is assessed at every step, not by collecting a union of asserted field names across an entire case. A payout assertion on the final step cannot conceal a missing payout assertion during submission. A payment assertion cannot substitute for checking event history.

Declared outcomeRequired observationsWhy
Evaluation HTTP-equivalent 200status, decision, payout_cents; reason also required for denied decisionsA decision alone does not establish the financial result
Successful submitstatus, claim_status, revision, payout_cents, event_count, payment_centsEstablish initial financial and history evidence
Successful approve/pay transitionAll six workflow observationsObserve state, history and ledger together
Successful readAll six workflow observationsReadback must inspect the stored business evidence
Rejected/error responsestatus and error; reason also required for 422 coverage denialDo not assert fields the error response does not contain

Zero and null are treated as values, not as missing fields. Before payment, payment_cents is null. After a legitimate zero-payout payment, payment_cents can be zero. The policy checks presence and response observability without converting one to the other.

For a rejected mutation of a claim already known in the case, a subsequent successful readback is required before another mutation of that claim. It must assert unchanged status, revision, payout, event count and payment. A read of another claim does not satisfy the guard. The declared before/after values must agree.

An unknown claim or a rejected creation has no previously established record to read successfully. Those error scenarios are not forced to invent payout or history fields. This distinction prevents a well-intentioned completeness rule from creating impossible tests.

4. Structural validity, completeness and correctness remain separate

validate_cases retains its structural valid flag and adds quality and review_ready. quality contains the policy fingerprint, a per-step required/missing field checklist, unsupported observations, rejection readback findings and a complete flag. review_ready requires valid structure and complete business assertions.

This separation is intentional. A malformed command-like case remains structurally blocked. A valid case missing payout remains visible for correction but cannot be approved. A complete case with the wrong payout can still be wrong; a reviewer must independently check expected values against the synthetic contract.

The assessment does not execute a draft, read the system-under-test result to manufacture expectations, fill fields, or silently rewrite a case. It identifies omissions and contradictions in the proposed observations. Existing wrong-oracle tests remain able to demonstrate an actual expected-versus-observed failure after an explicit engineering review.

The policy is business-observations-v1. Its fingerprint is stored with each new approval and run. An old approval without the current policy fingerprint cannot be executed or exported through the current server until reviewed again, even when its case is complete.

5. How generation changed

Local Ollama now receives an additional outcome-specific expectation schema, version complete-outcomes-v1. Successful workflow branches require all six observable fields. Evaluation responses require decision, reason and payout; error branches require only their returned error fields. Unsupported money/history fields on an error response are disallowed in the requested format.

The application stores the requested schema version and hash, prompt/hash, raw provider response and returned-schema diagnostics. It independently checks the returned data. A provider double or a model response that misses the requested format is not silently corrected. Structurally usable proposals remain inspectable with their completeness findings and raw evidence.

The default prompt strategy is assertions-v2. It instructs the model to follow the exact brief, include financial/history observations at each successful step, distinguish null from zero, count successful events, and read known claims after rejected writes. It repeats that errors do not return a complete claim view and that expected values must come from the written contracts.

The older named prompt strategies remain available for learning, but normal Studio generation uses the stronger format. The paired benchmark's loose baseline is a trusted internal evaluation path, not a new public API switch or an approval bypass.

6. Review, execution and export enforcement

Review revalidates the actual selected case data. It rejects selected incomplete cases with INCOMPLETE_ASSERTIONS and does not create approval. An unselected incomplete case does not prevent approving another complete case in the experiment.

Execution and pytest export perform the same completeness assessment again, as well as the existing contract, revision and case-hash checks. A matching stored hash or a stale review_ready field cannot bypass the current policy. Approvals that predate the policy receive STALE_ASSERTION_POLICY and require a fresh review.

New trusted pytest wrappers check the policy fingerprint and case completeness before calling the disposable runner. Previously downloaded wrappers remain offline snapshots; the server cannot revoke an already exported file. The new gates apply to current server-controlled execution and newly exported wrappers.

The underlying runner remains available to authored engineering tests and the explicitly labeled historical sensitivity exercise. That preserves the historical demonstration that narrow assertions miss known faults; it does not allow incomplete drafts through the current Studio review gate.

7. What the user sees

Each proposal now shows either “Business assertions complete · verify expected values” or “Approval blocked · incomplete business assertions.” Its expandable checklist names required and missing fields step by step. Readback issues identify the rejected mutation and the missing or contradictory later evidence.

Incomplete cases cannot be selected for approval. Their JSON remains editable. Saving a correction preserves the original raw generation, advances the revision and invalidates previous approval. The reviewer must still explicitly attest that expectations were checked.

Historical records are assessed through a read-only current view. Their saved case data, raw generation and old review history are not rewritten just because the policy changed. An old-policy approval displays a re-review message and cannot enable execute/export controls until renewed.

A browser regression demonstrates the complete learning path: generate a missing-payout proposal, observe the blocked checkbox and missing field, enter a reviewer note, explicitly correct the JSON from the contract, save, review and execute. No automatic value filling occurs.

8. Fresh local Ollama experiment design

The comparison made 16 real local requests: eight baseline and eight V5.2, one pair for every authored V4 task. All task inputs matched their references in both conditions. Every prompt and output schema was frozen before the first request, and pair order alternated to avoid always running the baseline first.

The baseline replay used the saved historical balanced-v1 prompts with the loose structural schema. V5.2 used assertions-v2 and the stricter outcome schema. Both used the existing qwen2.5-coder:3b model, temperature zero, seed seven and the same provider budgets. Model availability/digest and settings are recorded.

This compares the combined prompt/schema change, not the isolated causal effect of a prompt sentence. The eight tasks are reused educational examples, including previously exposed reserved examples; they are not a fresh held-out benchmark. There is one generation per condition/task, no repeated-seed estimate and no statistical model-ranking claim.

All raw cases remain unapproved and unexecuted. No output was repaired, omitted, or replaced by a fixture. The live result file and proposal JSON retain wrong values as well as missing observations.

The primary missing-field objective improved: all eight V5.2 drafts met the completeness policy, and all 51 required reference fields were present. The baseline omitted ten required fields and six of its cases were incomplete under the new policy.

However, the model filled several new fields with incorrect numbers. For the below-deductible case, it proposed payout 7600 instead of zero. It proposed zero payout for some 100000-cent workflow claims whose reference payout is 90000. It also produced wrong cap/deductible amounts on other monetary tasks. These values were not changed afterward.

This explains why reference-correct required fields rose to 45/51 while complete task passes fell from two to one. The stricter cases exposed additional incorrect assertions that the narrow baseline never made. V5.2 improves completeness and prevents missing assertions being approved; this experiment does not establish improved overall model correctness.

That distinction is the central result of this version. More filled fields are useful only when their values are reviewed. A future arithmetic-quality improvement should be a separately versioned experiment, preserving these results and testing independently derived expectations rather than learning answers from application output.

10. Regression tests and observed failures

Eight new original reproductions failed against V5.1 before implementation: missing evaluation payout, six omissions across submission/approval/payment observations, and a rejected payment without unchanged-state readback. Their original failure output is preserved in before-fixes.txt.

The expanded tests cover per-step gaps, false satisfaction through another step, unchanged readbacks, wrong-claim readbacks, another mutation before the guard, response-specific errors, zero/null handling, denied reasons, strict schema constraints, policy migration, execution/export rechecks and selected-only approval.

A complete authored lifecycle passes the normal runner and detects both known ledger_amount and history_skip fault profiles. This uses explicitly authored fixture data, not a claim that unapproved live drafts were executed. The retained historical fault experiments remain separately counted.

The browser test initially requested two cases while its fixed fixture returned one. The generation correctly recorded a response-count failure. I corrected the fixture setup to request one case, then reran the focused flow and full verifier. That test setup failure was not ignored or used to weaken production validation.

The core suite uses labeled provider doubles; the sixteen real Ollama requests are separate evidence. This keeps CI deterministic while retaining actual model limitations in the report.

11. Compatibility, state and prior versions

The structural DSL and synthetic claim contracts remain unchanged. Older cases can be inspected and edited; old incomplete cases cannot pass the current approval gate. Complete older cases need fresh policy-bound review. The current view makes this distinction without overwriting historical raw evidence.

V5.1's persisted leases, heartbeats, late-result fencing, explicit retry lineage and cache rejection remain active and are included in the full regression suite. The new generation flow uses those same operation controls, including the controlled baseline replay.

The local runtime was stopped, the original stores backed up under .local/backup-before-v5.2, and V5.2 started. Every original table row count and digest matched afterward, including 22 Studio experiments and three quality records. Existing approval data is retained historically; using an old approval now requires policy-bound re-review.

The live comparison store is separate from interactive state. Source packages continue to exclude mutable SQLite databases and browser/environment binaries. Earlier release ZIPs and their manifests remain preserved; the final preservation record verifies their checksums.

14. Outcome and remaining limitations

V5.2 closes the missing-assertion approval gap and makes required business evidence visible to both the model and reviewer. Successful workflow tests must assert payout, payment and history at each step; rejected writes on known records need unchanged-state readbacks. Error responses are not forced to assert nonexistent claim fields.

The live experiment demonstrates complete proposals, not universally correct proposals. Numeric reasoning, actor correctness and full oracle validity still require independent review. No raw live case was automatically approved or executed. Existing offline exports cannot be revoked, and the local application remains a synthetic learning framework rather than a real payer service.

VS Code was not opened or controlled. The detailed report, code, tests and preserved measurements are the reviewable result of this version.
