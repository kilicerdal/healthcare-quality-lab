Why the evaluator approach changed

V5.6 demonstrated an important limitation: a small local model could create useful workflow tests but repeatedly supplied incorrect expected evaluator values in a seven-step batch. The reference-assisted fallback made those cases safe to execute, but it did not establish that the AI had calculated the values correctly. V5.7 therefore separates model work into smaller requests, keeps the model's calculation visible, and measures raw output before any edit or repair.

Each generation now focuses on one exact evaluator input, one authored plan and only the relevant written rules. An inactive policy adds the eligibility rule; a network restriction adds the network rule; a zero amount retrieves the validation rule. Other plans and the workflow member/actor catalog are excluded from this focused prompt. The input and citations are fixed; expected values are left for the model to propose. Schema constants are not used to inject the correct payout.

The model supplies a structured assessment containing the decisive rule, decision, deductible, amount after deductible, cap and payout, alongside its declarative case. Denied and invalid requests have explicitly defined calculation semantics. This is a compact auditable calculation record, not an unrestricted reasoning transcript. The independent standard-library reference checks it separately from the case's assertions.

Why the installed larger model is an explicit option

The first 3B development pilot produced ten initial requests and seventeen correction calls before being stopped; a refined 3B pilot produced nine initial requests and eighteen correction calls before stopping. Interrupted attempts are retained. These were unsuccessful development trials, not a completed comparison or a hidden successful cohort. Their saved drafts show wrong response choices, arithmetic and assessment fields. They were not promoted as successful showcase tests.

The local machine already had qwen3.5:27b installed, in addition to the two 3B models. Its local runtime returned HTTP 501, structured output is unavailable, when sent constrained-format requests. Twenty failed compatibility requests are retained separately; they produced no completed AI answers and are infrastructure failures, not evidence that the model answered twenty questions incorrectly.

V5.7 explicitly supports two modes. The 3B models use the constrained schema request. The installed 27B model uses prompt-json-validated: the output schema is included in its prompt, constrained format is omitted, and think is false. The fixed loopback endpoint, allowlist, 90-second timeout, response-size ceiling and token/context budgets remain in force. All returned JSON passes the same application validators. The explicit thinking control follows the official Ollama API documentation. This is a declared model-specific mode, not a silent retry or model substitution. Raw provider metadata records the mode.

The full twenty-input 27B cohort was then run using this mode. The successful result cannot be attributed solely to a better prompt: both prompt design and model capacity changed. It does establish that the delivered local configuration produced the measured results without reference replacement.

How the twenty-case measurement was designed

The input set was frozen in tests/data/v57_evaluation.json before live generation. It contains fourteen existing core/alternate evaluator inputs from V5.6, split into individual requests, plus six explicit boundaries: zero, the deductible, deductible plus one, a below-deductible amount, the cap boundary and an above-cap amount. Literal expected outcomes are saved separately from the reference implementation and are not supplied to the generation prompt.

Each raw saved response is reparsed and checked independently of later edits. Raw correctness requires a matching assessment and a complete, reference-matching, fixed-input case. The separate literal-match field compares the model's assertion object with the frozen development expectation. AI-corrected children, reference-assisted children, stale contexts and unfinished work have separate counters. The dashboard describes its latest-100-experiment window and groups metrics by model in its JSON evidence.

How reviewed single requests become an E2E-compatible suite

The assembly endpoint accepts one to eight currently approved focused experiments with exact revisions. It checks their approvals, independent reference and focused metadata, rejects duplicate/equivalent inputs and assertions, and copies each step's inputs and expectations verbatim. It makes no model request and does not recalculate any expected amount.

The new suite starts unapproved and records full source cases, original approvals, assessments, origins and scenario fingerprints. Source rule and step budgets remain enforced. If the combined source assumptions exceed the DSL's four-entry limit, the suite explicitly points to the complete verbatim assumptions retained in its source snapshots; nothing is silently discarded. Reviewers can inspect those snapshots in Studio and exported provenance.

Origin labels distinguish an assembly of original AI expectations from an assembly containing AI corrections or other assistance. The successful seven-step evaluator assembly is labeled assembled_ai; the retained V5.6 workflow is original_ai. Both must pass a healthy execution before fault scoring. Copies remain frozen evidence even if a source draft is later edited; changes require another explicit assembly/review to enter the copied suite.

The two scenario gaps and what their tests prove

The zero-amount case sends commercial PPO medical evaluation with amount zero. It asserts 400 and INVALID_REQUEST. Merely citing HC-001 or storing an unreviewed draft cannot close the dashboard gap. A current reviewed case must match the explicit predicate.

The payment-replay case uses an M100 medical claim for 134,567 cents. Its expected payout is 124,567 cents. Submission records submitted status, revision/history 1 and null payment. Approval records revision/history 2 and still null payment. Payment records paid status, revision/history 3 and the exact ledger amount. Repeating paid returns 409 INVALID_TRANSITION. A final owner read proves the claim remains paid with revision/history 3 and the original payment amount.

A first 27B payment-replay request exceeded the existing 90-second provider timeout and produced no case; that failed experiment is retained. An explicit new request used the smaller constrained-output coding model for this workflow. This was an engineering model choice, not automatic provider fallback. The twenty-case 27B evaluator cohort remains separate from this workflow experiment.

That final read is essential: checking only a rejection response would not prove that the rejected operation left stored money and history unchanged. The case provides sequential replay evidence. It does not establish simultaneous-request race safety, database crash recovery or real payment-processor behavior.

What you can showcase and learn

You can demonstrate a complete loop: choose a risk, retrieve written facts, generate a visible model proposal, catch an incorrect oracle, review an exact snapshot, execute it, export a trusted test, and measure its ability to expose seeded defects. You can compare small-model failures with larger-model successes without hiding the failures. You can explain why a correct assertion is different from a plausible rationale, why an approved snapshot is different from a newly generated draft, and why a strong seed score is different from exhaustive quality.

Codex was used to implement and test the framework. Ollama performed the actual local inference. pytest, Playwright and GitHub Actions supplied independent execution evidence. Existing ChatGPT, Copilot and Claude Code learning exercises remain available, but they were not newly wired into the running application or falsely reported as model services used in this release.

The next useful extension is a genuinely reserved, independently authored evaluator set, broader plan/service combinations and repeated runs by model/version. A production system would also require real policy sources, authenticated reviewers, access controls, operational deployment design and domain validation. Those are separate engineering objectives. This release remains a synthetic healthcare quality lab with invented deductible/cap fixtures, no patient data and no actual financial payments.
