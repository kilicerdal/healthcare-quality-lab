# Healthcare Quality Lab V5.6 Engineering Report

## What we achieved and why we built it

V5.6 targets the ten controlled faults that survived the V5.5 two-case AI demonstration and makes the dashboard easier to present. The reviewed primary suite now detects **12/12 known fault seeds**, compared with **2/12** for the preserved baseline. The fair comparison records **ten newly detected profiles, zero regressions and zero remaining survivors** for this seed set. A separately authored alternate input set also reaches **12/12** after independent expectation checking and review.

These are AI-assisted results with explicit provenance. In the final refined run, both eight-step workflow cases were correct as generated. Both seven-step evaluator cases still needed bounded AI correction followed by confirmed independent-reference replacements. Each final two-case suite therefore contains one AI-authored workflow and one reference-assisted evaluator case. The dashboard and comparison show that source mix; the result is not described as twelve faults detected by flawless autonomous model reasoning.

The complete final deterministic suite passed **587/587 tests**: **480 unit, 66 API and 41 real Chromium browser tests**, with zero failures and zero skips. That is 32 more checks than V5.5.1. All seven retained evaluator and five workflow benchmark seeds continue to be detected. Desktop/mobile layouts, current versus historical evidence, interrupted operations, fair comparisons and provenance were checked.

The purpose is to turn a weak test result into a traceable improvement loop: inspect survivors, preview targeted input/action plans, generate expectations locally, check the reference, review a snapshot, pass healthy execution, score the faults and compare the evidence. More tests alone would not have established that improvement.

## Why the ten faults survived and how we target them

The old selected suite exercised a capped payout and a zero-payment workflow. That was enough to expose the removed-cap and skipped-history faults. It did not activate the other relevant conditions. A zero ledger cannot distinguish a correct amount from twice that amount; both are zero. A capped claim can hide skipped deductible subtraction when both results still reach the cap.

V5.6 derives target groups from actual survived profiles in a completed healthy-baseline score. It does not let model prose declare which faults were detected. Only a current score with current approved snapshots can initiate targeting. An implementation change or edited approval requires another score first.

| Former survivor | Targeting change |
| --- | --- |
| Eligibility | A covered service with active false, independently denied before benefit checks |
| Service coverage | A known service absent from the selected plan |
| Network | A covered, otherwise valid request with in_network false on a restricted plan |
| Authorization | A covered service requiring authorization, with authorized false and no earlier masking denial |
| Formulary | A covered prescription with formulary false |
| Deductible | An approved positive payout below the cap, so omitting the deductible changes the asserted amount |
| Ownership | A different known customer reading an existing claim |
| Duplicate replay | Repeating the same submission and reading unchanged state before another mutation |
| Approval skipping | Correct-role finance attempting payment before approval, followed by unchanged readback |
| Ledger amount | A positive paid amount, so doubling the ledger produces an observable difference |

The evaluator plan has seven ordered requests, including a capped control so the original limit detection is retained. The workflow plan has eight steps: submit, foreign-customer read, duplicate submission, owner readback, early finance payment, owner readback, approval and positive payment. Complete status, payout, payment, revision and event observations remain mandatory at successful steps. Error responses contain only their actual observable error fields.

These are authored input/action plans for known requirements. The model supplies the case metadata and expected observations. The provider schema constrains planned inputs/actions and cited sources without filling the expectation values. A separate sequence check rejects drift, including reordered steps, changed actors, missing rule citations and invalid claim-ID substitutions. Valid IDs can be consistently renamed while preserving identity relationships.

The alternate evaluator plan changes plan/service combinations and amounts, including outpatient and skilled-nursing examples. Its positive payout is 144,321 cents and capped payout 200,000. The alternate workflow uses member M200, reverses the foreign customer relationship and checks a positive payout/payment of 146,789. The literal expected answers were authored before inference. These are development variations, not a blind holdout or evidence that all plan combinations are covered.

## What changed in generation and correction

The first multi-step drafts exposed an ambiguity in the old general prompt: it said steps share state without distinguishing stateless evaluate requests from persisted workflow actions. A model could carry an inactive flag or denial from one evaluation into a later independent request. V5.6 explicitly resets omitted flags to true on every evaluate action; only submit/transition/read share stored claim state.

The survivor prompt also explains written-rule outcome categories at each workflow step. In particular, a different customer gets 403, a duplicate submission gets 409, and finance paying too early gets 409 INVALID_TRANSITION because the role is correct but the lifecycle state is wrong. This guidance comes from the written synthetic contracts, not observed application responses. Payout values are still generated and independently checked.

Every generated draft starts unapproved. Its target score, plan hash, selected group and inputs are saved before inference, so a process interruption does not lose its purpose. Retry and AI-correction children retain that context. Reference-assisted children retain it as well. Manual case edits are labeled reviewer edits instead of retaining a misleading AI-output source label; the previous origin and original raw generation remain in history.

The existing two-attempt correction budget remains shared across each correction history. Wrong corrections do not become approvals. Reference assistance uses an inspected replacement preview and explicit engineering confirmation, creates a separate unapproved child and is labeled separately from a successful model correction. Product UI actions remain explicit clicks; the opt-in engineering measurement operator authorizes its bounded repair sequence separately.

A measurement-helper issue was found during the first run: correction returns a saved record, while derived target/readiness assessment is obtained through the current detail view. The helper now reloads that assessment after every correction. A regression test verifies two calls remain bounded, reference assistance remains unapproved and every resulting source label survives into scoring/comparison. Earlier failed drafts and the initial incomplete measurement were retained rather than replaced.

## How fair comparison is enforced

A comparison accepts two completed error-free scoring records. Their implementation, contract, reference and assertion-policy fingerprints must agree. Their fault-profile sets and applicable denominators must also match. A partial score, execution error, changed implementation or changed denominator is rejected instead of producing an inflated before/after percentage.

Each profile is labeled before and after. Newly detected faults, regressions and remaining survivors are separate lists. A reverse comparison exposes the ten regressions instead of hiding them. Historical records remain inspectable, and current implementation/approval changes are marked explicitly. Comparison controls offer current compatible implementation records; saved older evidence remains available separately.

Neither a duplicate case nor multiple detections of one fault inflate the suite numerator. Healthy baseline execution must pass first. Infrastructure failures do not receive fault-detection credit. Applicability remains the documented action-family definition used in V5.5, so the preserved two-case baseline and new two-case candidate both use twelve applicable known profiles.
