## Concurrency and interrupted payment recovery

Two actual loopback HTTP clients begin from a barrier and request payment for the same approved claim. The expected outcomes are one HTTP 200 and one HTTP 409, with exactly one ledger entry, payout 90,000 cents, revision three and three committed events. SQLite serializes writes; this does not establish distributed-system scalability.

A separate demonstration starts an actual child process, performs payment/state/history writes through the existing service, and exits before commit. SQLite rolls back those uncommitted writes. A new service can retry successfully; replay is rejected without changing state. The interruption hook exists only in the disposable demonstration store, not in the production workflow implementation.

## Trustworthy expectations and requirement changes

An authored case incorrectly expects the full 112,345-cent amount. The independent checker requires a 102,345-cent payout after the 10,000-cent deductible. The corrected authored control passes healthy behavior and detects a seeded skipped-deductible defect by assertion mismatch. It is not represented as a fresh AI generation or human approval.

Literal arithmetic anchors and monotonicity/bounds/replay invariants exercise the independent reference. Anchors also freeze the intended teaching-plan constants so a shared JSON change cannot silently move both implementations together. These examples were authored for engineering review; no external clinical or human-expert validation is claimed.

A child-process what-if changes the deductible to 15,000 cents. The reference computes 97,345 cents, a previously matching approval becomes stale, and actual Studio execution is blocked with STALE_REFERENCE. Running application fixtures, user databases and other requests remain unchanged.

## Provider comparison and repeatability

The new frozen cohort contains sixteen inputs different from the prior V5.7 cohort, with three trials per provider. It measures model-proposed expectations and compact calculation records inside an authored case wrapper. Both providers use the same base inputs, rules, prompt and schema; transport, model size, hardware and decoding differ. This is a small development evaluation, not blind-holdout performance, a causal model comparison or a general accuracy score.

Both providers completed 48 trials, with 48/48 schema-valid, complete assertions and matching literal expected outcomes. OpenAI GPT-6.1 Terra also matched 48/48 calculation records; qwen3.5:27b matched 42/48. The six local rejections were the inactive and denial-precedence inputs in each trial: expected denial/payout were correct, but deductible/cap/payout calculation fields were null rather than the required plan facts/zero. No provider transport errors occurred.

Both providers produced identical expected outcomes across repeated trials for all sixteen inputs. All three trials were eligible for sixteen OpenAI inputs and fourteen local inputs. Local fixed temperature/seed and prompt-JSON mode differ from OpenAI low reasoning and strict structured output. Median observed latency was 2,223.915 ms for OpenAI and 9,751.835 ms locally. These observations do not support a general speed/quality ranking.

The OpenAI comparison used a $0.04056010 token-derived estimate; the separate one-request pilot brings the ledger total to $0.0421751 over 49 requests. Conservative reservations total $2.687437 against a $15 cap, with zero unresolved requests. Unused reservations were not released. These values are not an account billing invoice. Raw failures, outputs, settings and usage remain in artifacts/showcase/provider-comparison.json. Outputs remain unapproved and none was automatically executed.

OpenAI uses the Responses API, strict structured output and store=false. Paid access exists only in an explicit CLI, requires --allow-paid, and uses an existing key read into memory. No credential is committed or copied to this project. A persistent SQLite ledger serializes reservations, enforces at most $15, never releases unused allowances, and blocks subsequent calls after uncertain charges. No hidden retry or provider fallback exists. Usage-derived estimates are distinct from conservative reservations and from billing invoices.
