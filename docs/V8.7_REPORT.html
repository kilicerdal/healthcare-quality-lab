Healthcare Quality Lab V8.7 Engineering Report

What we are building and why

V8.6 corrected two known model failures and passed two new numeric variants. That was useful evidence for the targeted fixes, but four cases could not establish general reliability. V8.7 connects the accepted improvements into an evidence workflow: broader sealed scenarios, repeat trials, rule review, stateful claim journeys, AI-only defect scoring, reproducible model evidence, failure investigation and saved showcase replay.

The work is confined to /Users/erdalkilic/Documents/Healthcare Quality Lab, on codex/v87-reliability-evidence. Existing sibling projects are outside scope. VS Code is not used. All policies, identities, claims and money are synthetic. This release does not certify real Medicare or commercial coverage correctness.

The purpose is to make a passing test meaningful. We need to know whether the model predicted the right value, whether the independent reference itself agrees with the written rules, whether account history works across claims, and whether the generated assertions detect defects. Those are separate questions and receive separate evidence.

Preserve the successful protocol and assess unfamiliar inputs

The model instructions, schema, two-stage generation and post-freeze independent checker remain those of V8.6. V8.7 changes the input cohort and study controls, rather than tuning the prompt against new answers. The model still authors coverage decisions, deductible remainders, financial values, account usage, lifecycle observations and ledger expectations. No calculator or application answer is supplied to inference, and no number is repaired after generation.

After the first nine simple scenarios, the hospital and mixed scenarios receive one preselected repeat each before the final three stateful scenarios. This order is fixed before inference so a later complex-case timeout cannot erase all repeat evidence. Repeated exposed inputs are excluded from fresh accuracy. The study tracks both repeated pairs passing and identical answer hashes; consistency does not imply correctness.

The model is the installed qwen3.5:27b using the existing provider settings. The fixed ceiling is 28 model calls, 180 admitted seconds per case and a 2100-second admission window. There is no retry, resume, self-review, model swap or budget extension. A full-case allowance must remain before another trial starts. Provider uncertainty stops all further requests so unknown backend work is not followed by more inference. Skipped and interrupted trials remain in the denominator, and incomplete assessment does not receive a completed accuracy percentage.

Fresh means first model exposure in this frozen study. Reference-backed offline engineering fixtures validate the harness and schema, but are not AI accuracy evidence. This is not an externally conducted blind human study. After publication, these inputs are exposed and cannot be labeled fresh in a later rerun.

Independent checks on the reference rules

A separate authored rule-review module stores ten fixed examples with literal expected results and written reasoning. It checks the Fraction reference calculator and production calculator against those literals. Neither calculator creates the expected values.

Examples include floor coinsurance at a one-cent boundary; other payer before deductible; a family deductible with only 500 cents remaining; a family OOP with 100 cents remaining; July copay selection; 2027 policy selection; and benefit-cap excess that must remain noncovered rather than become OOP. The large-claim examples make the distinction concrete: an allowed amount of 300000 cents produces 200000 payer, 30000 member and 70000 noncovered under the specified synthetic H1 policy.

This guards against a shared implementation error being accepted merely because two calculators agree. A negative control perturbs a calculator and confirms the authored vectors fail. These examples are engineering review aids, not an independent person's sign-off. Independent human review remains explicitly pending.

Stateful journeys and actual execution

Reference-authored engineering journeys cover the twelve study inputs plus additional cross-claim credit and year-reset cases. The cross-claim case submits three family members' claims, then pays, adjusts and reverses the first claim before reading the later claim. It checks that only the original allocation is credited, later claims are not repriced, and family usage reflects the surviving allocations. The year-reset case verifies separate service-year balances while retaining the original year's history.

These journeys execute through disposable state. The final evidence build also runs them through actual HTTP endpoints, recording full requests, responses, assertions and request IDs. They are attributed as reference-authored engineering tests, never as model-authored tests. No interactive claims or approvals are changed by these runs.

Defect-detection scoring with separate attribution

The evidence builder rechecks every frozen model answer, hashes the original files and admits only eligible original first-attempt cases. Repeat trials, wrong predictions, incomplete records and repaired cases cannot earn AI defect credit. Semantically duplicate AI cases are removed before scoring.

Both the AI suite and reference-authored engineering suite run against the same catalog of trusted production-pricing AST mutations. Healthy baseline execution and independent expected-value matching are prerequisites. Each mutation has an ID, detection result and witness; survivors stay visible. No model-generated executable code is compiled or run. Suite sizes are disclosed, so this is not an equal-budget claim that AI outperforms authored testing.

Reproducibility and failure investigation

Raw records preserve exact prompts and responses, model digest and settings, schema/prompt/cohort/source fingerprints and stage timings. Per-file SHA256 values link the study outcome to the immutable raw trial. A content hash seals the assembled dashboard. Missing or tampered evidence is rejected; stale evidence is labeled historical instead of current acceptance.

Post-freeze investigation packets bring together the relevant rule IDs, every operation, independent account history, model worksheet differences and complete raw model calls. Failed assertions receive evidence identifiers. These reference observations are for investigation after generation and are never fed into the study's next stage as corrections.

The existing optional AI explanation tool remains available for evidence-backed hypotheses; no additional provider or cloud cost is introduced. V8.7 does not label deterministic analysis as an AI explanation. An explanation cannot approve, repair or execute a test. Ollama's role is expected-value generation, the coding assistant's role is implementation, and independent deterministic checks decide acceptance.

Dashboard and one-command showcase

The responsive /reliability page displays fresh passes, call usage, repeat pairs, authored rule checks, observed latency, scenario outcomes and separate AI/authored mutation scores. A trial selector exposes investigation packets and provenance. The interface renders saved text with safe DOM APIs. Page load and refresh make zero model calls and perform no mutations. An integrity failure prevents scores from displaying; a source mismatch is visibly historical.

python -m tools.reliability_showcase starts saved replay and prints its URL. An explicit --build scores saved evidence and runs disposable HTTP journeys without inference. An explicit --fault-demo uses the existing isolated known-defect rehearsal: healthy execution, a one-cent payout fault, failed assertion and restored healthy execution. The fault never patches the interactive server.

See docs/V8.7_GUIDE.md for commands and the presentation sequence. A demonstration should show a blocked wrong prediction as well as a passing case, then show a caught defect. This explains the framework's value without waiting for live model generation.
