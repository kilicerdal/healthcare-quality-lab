Healthcare Quality Lab V7.0 Engineering Report

November 18, 2026 · Standalone project: /Users/erdalkilic/Documents/Healthcare Quality Lab

Why we built V7.0

The earlier versions built useful controls, but an outside reviewer still needed a coherent path through them. V7.0 packages V6.8–V6.12 as a reproducible engineering workflow with an explicit starting point, preserved history, readable reports, actual browser evidence and release validation. It also hardens the boundaries exposed as those components come together.

What we built and where

All work remains in the standalone Healthcare Quality Lab. portfolio.py, portfolio_api.py and static/portfolio.js add a guided showcase at /#journey. Six steps lead to test design, review/HTTP execution, failure investigation, requirement traceability, test effectiveness and frozen model comparisons. docs/V7.0_DEMO.md supplies commands and a reviewer talk track; the six detailed version reports explain purpose, design, files, tests, results and limits.

The first guided action loads a clearly labeled authored control. It creates no AI answer, approval or execution. The reviewer must inspect the independent result, enter a review note and request execution separately. This makes the trust boundary visible instead of hiding it in a polished replay. The original workspaces and older proof pages remain available.

Fresh replay and historical accuracy

The existing fresh-demo launcher still refuses to overwrite nonempty state and installs dependencies only inside this project. The expanded seed retains its original two-to-twelve known-defect demonstration and adds saved V6.8 design and V6.12 comparison evidence with explicit replay labels. Original model outputs, source fingerprints and failure outcomes are preserved. Replaying a record is not a new inference, and historical proposals cannot silently export under a new fingerprint.

The guided overview compares verification to the current implementation fingerprint before calling it passed. Old passing results become stale when implementation changes. New generation/comparison panels also distinguish historical snapshots from current ones. Requirement coverage cannot inherit a passing execution from an edited case or stale approval.

Persistence, identity and error boundaries

Readiness now checks all new design, advanced-investigation, traceability and experiment stores. Tests prove that removing any required store returns an unavailable readiness result. All new endpoints remain under the existing advanced authentication/role boundary, and writes retain CSRF protection in shared mode. Loading a control as an analyst never impersonates a reviewer or approves it.

Invalid explanation JSON is retained as rejected raw evidence. Explanation requests are recorded before the provider call; provider failures are saved and an unresolved or completed request cannot silently retry. A separate investigation is required for another explicit attempt. These measures distinguish unavailable inference from a wrong financial answer and prevent a failed request from disappearing behind a generic UI error.

The known-defect rehearsal executes trusted fault code in a child process, not inside the interactive server. The mutation comparison remains an explicit offline experiment. A read-only scorecard cannot patch production dependencies. Generation, cancellation and source-bound approval controls remain independently tested.

V6.9's actual local explanation cited the real failed assertion and agreed with the deterministic category, with uncertainty. Citation existence and category agreement do not verify every sentence.

This sample does not show that the focused prompt improved raw reasoning. No reference-assisted correction is mislabeled as raw success, and no new paid API is introduced.

Final hosted defect and accepted patch

The first complete hosted sweep on the unreleased V7.0.0 tag caught a WebKit startup race in the original AI Studio. Its generation button was enabled while model, strategy and rule configuration were still loading. An early click could post empty selections and never create the intended proposal. This was a real UI readiness defect, not an incorrect financial expectation or an infrastructure excuse.

The fix disables Generate in the initial HTML, shares one initialization promise, waits for configuration and saved-record hydration, and enables generation only after successful initialization. A programmatic submit before readiness is blocked too. A deterministic browser test holds the configuration response, verifies zero generation requests and a disabled button, then releases it and asserts exactly one complete request. Existing generation/correction/review journeys are rerun across all three browsers. No fixed sleep or relaxed assertion was substituted.

The first readiness patch was V7.0.1 within the requested V7.0 milestone. The earlier unreleased V7.0.0 tag is preserved rather than force-retargeted. Its successful 906/1040 local runs and failed hosted sweep remain pre-patch evidence; the patch's final receipts below are the publication gates.

Research-hub readiness and V7.0.2

The next full hosted run confirmed the Studio fix but found a separate early research-action issue. The failed WebKit log contained no POST to the rule-impact endpoint while initialization requests were completing. Research actions were available before the complete hub metadata/layout was ready. We did not call this a product calculation defect, increase the timeout or retry until the report looked green.

The combined fix disables research rule-impact, follow-up generation, investigation, maintenance and benchmark actions in the initial markup. Initialization now waits for the legacy overview plus advanced, integration, design and experiment metadata before enabling them. A deterministic test holds the advanced-experiment metadata response, verifies disabled rule actions and zero impact requests, then releases it and observes exactly one correct HC-007 impact request with no model call. Both readiness fixes and associated journeys passed 60/60 checks across the three browsers. The accepted publication is V7.0.2; both earlier tags and failed hosted runs remain development history.
