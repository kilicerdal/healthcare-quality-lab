# Healthcare Quality Lab V6.9 Engineering Report

November 18, 2026 · Standalone project: `/Users/erdalkilic/Documents/Healthcare Quality Lab`

## Why we built this version

A failed generated test does not automatically mean the application is defective. The expectation may be wrong, evidence may be stale, or the harness may have deliberately changed an observation. V6.9 turns failure investigation into a reviewable engineering workflow that distinguishes those possibilities before asking a model for an explanation.

## What we built

The advanced runner now retains each synthetic request, actor, action, full response snapshot, assertion differences and HTTP request ID. `evidence_investigator.py` packages the frozen cases and execution into a content-hashed bundle. It verifies the bundle, case/result cardinality and assertion snapshot consistency before classifying results. `investigation_api.py` stores new investigations separately in `investigations-v69.sqlite`; existing legacy investigation behavior remains available.

The engineering hub shows observed expected-versus-actual facts with stable identifiers. A separate button requests one local AI explanation of saved evidence. Merely opening a page, listing investigations or rehearsing the deterministic control makes no model request. The model receives observed evidence and an explicit uncertainty requirement, not permission to fix code, approve tests or change the ledger.

## How the known-defect story works

The authored demonstration runs a correct advanced case through actual loopback HTTP, temporarily perturbs the production pricing dependency by one payout cent, observes the failure, restores the original function and reruns the healthy case. It records all three results. This is a named trusted engineering fault control, not an observed unseeded defect or AI discovery claim.

The interactive server never patches its own pricing dependency. It launches a bounded child process for the rehearsal, using fresh temporary claim stores. This prevents a fault demonstration from contaminating unrelated interactive requests or payments. Only the named control is permitted; neither browser nor model can supply source code, a shell command or an arbitrary peer endpoint.

## Classification and AI grounding

Deterministic triage distinguishes potential application faults, expected-value errors, stale evidence, infrastructure uncertainty, harness observation injection and passing results. For example, the existing observation-fault mechanism is explicitly labeled a harness injection, while a reference-matching case that fails against the perturbed production dependency supports a possible application fault. Neither classification proves a general root cause.

AI answers use a strict schema containing hypotheses, categories, cited fact IDs and uncertainty. The evaluator rejects citations to missing evidence and separately measures agreement with the deterministic category. This is deliberately narrower than claiming the prose is fully verified: a real fact identifier can still be cited in a misleading sentence. The report and UI keep the hypothesis label visible, and no accepted explanation automatically changes code or test approval.

Evidence content hashes detect alteration relative to the saved bundle; they are not digital signatures or protection against a privileged actor replacing the bundle and its hash together. A changed source/contract produces stale classification instead of silently treating an old result as current.

## How we validated it

Unit controls cover the actual one-cent defect and restoration, wrong expected values, stale source, corrupted bundles, harness injection, hallucinated citations and real HTTP request/response capture. API checks cover invalid requests and saved isolated rehearsals. The first browser run found a DOM ID collision with the preserved legacy investigation panel. The new panel now uses its own evidence-prefixed IDs; the legacy controls remain intact. A Chromium journey asserts the visible 71200-versus-71201 difference and the restored healthy result. `tools.capture_investigation` can retain an actual Playwright trace, screenshot and source-linked capture receipt from the same journey.

The actual local AI explanation experiment is retained separately from offline provider controls. Its citation/category rubric is reported as observed, including failure if the model invents unsupported evidence. No paid API is used, and the explanation is not mixed into test-generation accuracy.

## What we achieved

We can now show a connected engineering argument: a trustworthy expectation detects a controlled product behavior change; concrete request/response evidence supports the difference; deterministic triage narrows the category; AI offers a cited explanation; restoration passes the original case. This is more useful than an ungrounded chat answer claiming to know why a test failed. V6.10 will connect these facts to versioned requirements and maintenance impact.
