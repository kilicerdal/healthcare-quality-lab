# Healthcare Quality Lab V5.9 Engineering Report

## Why this milestone exists

A failed assertion does not by itself prove that the application is defective. The expected value may be wrong, an assertion may be missing, the environment may have failed, or the evidence may refer to an old contract. V5.9 adds a grounded investigation workflow that makes those distinctions visible before asking AI for an explanation. All implementation is in `/Users/erdalkilic/Documents/Healthcare Quality Lab`. Other projects were not modified. VS Code was not opened. These milestones are delivered together in the V6.2.0 checkout; older published releases remain separate historical evidence.

## Implementation and evidence flow

`healthcare_quality/investigator.py` reads a stored run and its frozen approved cases. It compares the case with the independent calculator and assertion policy, then derives categories: passed, stale evidence, infrastructure error, test-oracle error, incomplete assertions, potential application fault or insufficient evidence. Potential application fault remains a hypothesis requiring reproduction, not automatic defect confirmation.

The output links requirement IDs, rule-version hashes, case hashes, experiment/run IDs and observed assertions. Failed fields have evidence IDs and explicit expected/observed values. No original run, draft or approval is changed. The record is saved in a separate research store and can be reopened through the engineering hub.

The existing local investigation service is retained. Its rule retrieval now prioritizes a failed financial/history field's relevant source before other case citations, preventing a payout failure from losing HC-007 behind unrelated rule IDs. If the user explicitly requests AI hypotheses, the model receives extracted facts and selected written sources. JSON schema checks restrict evidence/source citations and confidence labels. Valid IDs do not prove semantic support, so the deterministic result stays separate from model prose.

The hub presents a readable classification and optional explanation, plus full JSON for inspection. Saved investigations have their own selector. Changed-rule analysis identifies linked eligible and unreviewed tests and explicitly labels citation-based impact as incomplete. A separate action asks Ollama to propose a boundary test; that draft still passes all existing validation and review gates.

## Actual local AI demonstration

A retained case expected 91,000 cents for a 100,000-cent commercial PPO evaluation. The application's observed value was 90,000. Deterministic classification identified a test-oracle error. One actual `qwen3.5:27b` request produced a validated explanation: subtracting the written 10,000-cent deductible gives the observed 90,000, so the expected value may be wrong rather than the product.

The full prompt, extracted facts, source citations, raw response and explanation are retained in `artifacts/v5.9/live-ai-investigation.json`; the separate classification is in `grounded-classification.json`. Its recorded state is `explained`. This was a real local inference, not a provider double. It did not repair or approve the old case.

## Maintenance and safety controls

`maintenance.py` recommends a smaller suite using a greedy cover of actually observed known-seed detections. The API requires a current score and current approved snapshots. It does not delete tests, prove a mathematical minimum or preserve unmeasured semantic coverage. Repeated-run comparisons group matching source, contract, revision, transport and fault profile; intentional seeded failures cannot create a false flaky-test warning.

Adversarial-output tests demonstrate that shell/tool/code-shaped responses cannot become executable cases. Model prose and requirements remain untrusted data. Source selection, typed observations, immutable snapshots and fresh review are enforced independently of AI explanations.
