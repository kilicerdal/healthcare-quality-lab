Healthcare Quality Lab V6.10 Engineering Report

November 18, 2026 · Standalone project: /Users/erdalkilic/Documents/Healthcare Quality Lab

Why we built this version

A passing test suite cannot explain coverage if it cannot connect its assertions to the rule being tested. A list of citations is especially weak: a generated case can cite every rule without exercising all of them. V6.10 builds an inspectable chain from a versioned written requirement to a scenario, its individual assertions and recorded execution evidence.

What we built and where

healthcare_quality/traceability.py derives requirement dependencies from bounded case actions and maps rule families to relevant observed fields. Each written rule has a content version that conservatively includes shared synthetic plan and effective-policy facts. The graph includes scenario hashes, declared citations, derived dependencies, assertion nodes, execution nodes and typed links. traceability_api.py exposes current graphs, durable snapshots and a what-if change analysis; snapshots use a new traceability-v610.sqlite store.

The engineering hub presents seven requirement rows showing scenario count, assertion count and current passing coverage. The complete graph remains inspectable as data. It distinguishes a saved execution from current passing evidence: stale source, changed contract, changed case content or missing review cannot inherit a previous passing result. An unexecuted case does not count as a passing test.

How dependencies and versions work

Money, effective-date, coverage, coordination and accumulator dependencies are conservatively inferred for benefit cases. Payment, reversal and adjustment actions add the financial lifecycle rule; appeal/resolution actions add the appeal rule. This avoids crediting an adjustment-only case for appeal coverage merely because the model listed the appeal rule in its citations.

Assertions link to the rule families they observe: policy/status, partial/noncovered results, other-payer amounts, payout/member amounts, member/family accounts, revision/history/ledger and appeal state. These are explicit observability mappings, not an automatic proof that each clause of a business requirement has been tested. Some mappings are deliberately conservative and can produce extra maintenance candidates.

Requirement versions hash written text with shared plan/policy facts. Including all shared facts may invalidate more candidates than a perfect semantic dependency analyzer would. That is preferable to claiming a precise dependency the tool has not established. The existing source/contract-bound review gate remains the execution authority; this graph does not invent a second independent approval mechanism.

Rule-change maintenance without silently changing the application

A reviewer can save a graph snapshot and propose bounded replacement text for one or more known written rules. The tool compares versions and returns affected scenario identifiers, the changed rule links and a recommendation to inspect/regenerate expectations and review again. The UI demonstrates this with a proposed BN-004 cost-sharing change.

This is a what-if analysis. It does not overwrite policy files, rewrite saved expectations or approve a regenerated case. If the actual application contract changes later, its normal fingerprint check blocks old execution approvals. Historical evidence remains available rather than being rewritten to appear current. Unknown rule IDs, duplicate changes, unexpected fields and malformed text are rejected.

How we tested it

Unit checks verify that overbroad citations do not invent appeal coverage, an approved passing snapshot can contribute current coverage, stale approvals and changed cases cannot do so, unchanged text has no spurious impact and proposed changes leave original rules/cases untouched. Negative inputs and malformed saved proposals are exercised. API tests connect an imported unapproved case to a stored graph snapshot and prove the impact preview leaves it unapproved. The Chromium journey follows the same path through the actual UI.

No AI call is required to build the graph or calculate change impact. This keeps traceability reproducible even when Ollama is unavailable and avoids turning an AI explanation into dependency authority.

What we achieved

We can now answer which requirement a financial assertion observes, which scenario contains it, whether it actually ran and whether the approval still matches current code. We can also demonstrate maintenance impact without damaging the current synthetic policy or falsifying historical results. V6.11 will use these linked assertions to assess whether tests detect actual bounded implementation changes rather than merely passing healthy behavior.
