Healthcare Quality Lab V8.1 Engineering Report

Outcome and purpose

Measured outcome: the 27B model passed 5/10 strict first attempts and 5/10 blind reviews; the 3B model passed 0/10 in both stages. Neither met the predeclared 80% target. The engineering implementation passes its checks, while model-only prediction remains experimental.

V8.1 adds a separate experimental path in which local Ollama authors every expected value. The framework supplies the business rules and fixed claim actions, then checks the completed predictions independently. It never replaces a wrong prediction with a calculator answer in this path.

The practical problem was the earlier 0/16 eligible raw expectation answers: a model could produce valid JSON and still invent the wrong payout, payment status, used accumulator, revision or history count. A professional framework needs to expose those errors, measure whether a change helps, and prevent an attractive but incorrect test from receiving approval.

What was built and why

1. Fixed inputs, model-authored expected values

The new expectations-only protocol gives the model an immutable scenario: actors, actions, claim inputs, dates and step IDs. The model returns observations keyed to those steps. The server assembles the original inputs with the returned expected values, without rewriting those values.

This prevents a model from making its answer appear correct by changing the claim amount, removing a difficult payment step, changing the actor, or replacing the scenario. Input preservation is a server guarantee; it is not evidence that the model learned to follow inputs better. Missing, duplicate or reordered observations are rejected.

2. Numeric and state worksheets before the answer

Each model observation begins with a calculation worksheet, followed by the expected API observation. The monetary worksheet names eligible cents, deductible, copay, coinsurance base, payer before caps, member before the out-of-pocket cap, payer after that cap, final member/payout/noncovered amounts. This ordering gives the model a structured sequence before it commits to its final financial answer.

A separate state worksheet records stored revision, event count, ledger count and ledger cents before and after every action. This directly addresses the development failure in which the larger model calculated money correctly but left payment revision/history counters unchanged. New payments increment counters; reads do not; identical replays return the original response without adding another payment or event.

All monetary quantities remain integer cents. Rules state floor division, other-payer-first allocation, used accumulators rather than limits, policy dates, annual reset, zero payments and replay behavior. The free-text accounting note is unverified model text. Only the disclosed numeric worksheets and observations receive strict correctness credit.

3. Rules without answer leakage

Prompt construction reads the raw policy, plan and identity facts needed by the fixed scenario. It does not execute the application calculator, the independent reference calculator, the Oracle, or a scenario compiler to obtain expected answers. Tests replace these functions with failures while constructing prompts, proving that construction does not call them.

Rules and arithmetic formulas are legitimate input. Ready-made numeric answers, application responses and evaluator feedback are absent. The model computes all supplied expected values itself. Post-freeze independent checking still uses the reference: removing a calculator from generation does not require removing independent quality control.

4. Optional blind self-review

One optional second request gives the model the same rules and its own original output. It receives no reference answer, grade, mismatch list or application response. Both responses are saved before independent evaluation begins.

First-attempt accuracy and self-review accuracy are reported separately. A self-review recovery never retroactively improves the first score, and a self-review regression remains visible. There is no hidden retry or repair loop. A provider failure without an original answer receives no invented review request.

5. Durable bounded experiments and provenance

The new SQLite experiment store retains planned trial rows, exposure history, prompts, JSON schemas, final provider output, model digest, options, timing and stage assessments. Leases, heartbeats, restart recovery, cancellation and late-response fencing protect interrupted jobs. Page loads, status reads and saved replay make zero inference requests.

A maximum of 24 requests per experiment includes every stepwise request and optional self-review. Whole-case and stepwise strategies are supported; stepwise mode sees only its own previous predictions, never actual application observations. The measured qualification uses the locked whole-case strategy.

Source, contract and cohort hashes bind every run. Source changes during a run invalidate its use. Aggregation rejects mixed versions, source/cohort hashes, model digests, provider profiles, native-reasoning settings and duplicate trial identities. Planned failures remain in the denominator rather than disappearing from the score.

6. Dashboard and separate approval

The existing V8 workbench now contains an experimental expected-value panel: explicit start, model/input/strategy selection, blind self-review, saved experiments, refresh, cancel, stage scores and export. Controls wait for initialization, and configuration errors leave generation disabled. Desktop and phone browser checks cover the new flow.

An export independently rechecks the frozen output and creates an unapproved proposal. It copies model values unchanged. The existing review and actual HTTP execution steps remain separate. Incorrect observations or worksheets block export. Calculator-assisted legacy paths remain available with their existing provenance; they do not receive model-only credit.

Frozen qualification design

Before the first reserved request, the implementation was committed as 8ba1cad06fe8b1d94ef7d2357fb793c247d8efc0. Its measured source fingerprint is 039fa265fd6b6e2fc8aac9c22f34ac03cba10edfa2a029e291b8f9107a182065. Protocol expectations-only-v81-6 and the complete two-batch plan are in artifacts/v8.1/protocol-lock.json. No implementation tuning occurs during this experiment.

Two installed models receive the same ten reserved scenarios, one first attempt plus one blind self-review each: at most 40 requests, split into two 20-request durable experiments. The target is at least 8/10 strict first-attempt passes per model. All planned rows, including provider failures, stay in the denominator. A strict pass requires valid schema, complete correct observations, and correct monetary/state worksheets. The UI remains experimental even if a selected-cohort target is met.

The reserved scenarios cover Part B outpatient, Part A hospital with an out-of-pocket cap, Part D with another payer, dental below deductible, out-of-network vision, mixed PPO covered/noncovered lines, unauthorized Advantage hospital with zero payment, HMO July policy change, a new-year account reset and identical payment replay. All benefits and amounts are synthetic teaching fixtures, not real Medicare or commercial coverage guidance.

A fresh local exposure ledger does not prove absence from a model's training data. One deterministic trial per input is a bounded engineering measurement, not repeatability or population-wide accuracy. The old 0/16 and this new ten-input cohort differ; they cannot support a matched before/after accuracy claim.

How to use and learn from V8.1

Open the fresh local showcase at http://127.0.0.1:8901/#workbench. The V8.1 panel can load the recorded actual experiments without inference. Each saved batch contains five reserved inputs per model; the published aggregate scorecard combines all ten. Select a saved record and refresh its status to inspect its original/model-review outputs and independent assessments.

Starting a new experiment explicitly calls the selected installed local model. Export an eligible row and stage to a new unapproved proposal, inspect its financial and lifecycle assertions, then separately review and run actual HTTP. Replaying a recorded case does not become a new AI accuracy trial.

The guide provides CLI commands, request budgets, profile settings, whole-case/stepwise boundaries, cancellation/restart behavior, score interpretation and troubleshooting. The architecture document maps each boundary to its implementation. ChatGPT, Copilot and Claude Code remain optional learning companions; this milestone does not claim to have invoked those products. Actual generation used only the two installed local Ollama models.

What we achieved and what remains

We now have a working, inspectable model-only expected-value pipeline with immutable inputs, arithmetic/state scaffolding, separate blind self-review, durable provenance, independent checking and governed execution. It can demonstrate actual successful model-authored tests without borrowing calculator-produced expected values, while refusing the failures.

The framework's deterministic engineering checks pass, but model reliability is a measured limitation, not a promise. Passing a small synthetic cohort would still require broader inputs and repeated trials before generalization. Missed targets remain visible and experimental. Further improvement should use new development cases, versioned protocols and a genuinely new reserved cohort; tuning against these now-exposed qualification inputs would require labeling the result as development.

The next useful experiment is to isolate cap transitions, noncovered accounting and longer state transitions in development, compare direct versus stepwise prediction on a fixed bounded budget, and rerun untouched qualification inputs with separate first/review scores. More AI tools should be added only with recorded provenance and a clear learning purpose; they should not inflate the number of tools credited with the same result.
