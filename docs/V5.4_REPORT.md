# Healthcare Quality Lab V5.4 Engineering Report

## What we built and why

V5.4 fixes both AI-generated tests that remained incorrect after V5.3 and improves the correction workflow around them. The underlying claims evaluator did not need a payout-rule change. The defect was in the tests' expected results: one used the wrong subtraction near the deductible, and the other applied the cap incorrectly. Changing a correct application to satisfy those assertions would have hidden the real problem.

The retained 10,001-cent case now expects a payout of **1 cent**, replacing 9,001. The retained 286,450-cent case now expects **200,000 cents**, replacing 186,450. Real local Ollama responses produced both repairs under the new correction prompt. Both cases passed reviewed execution, and their two exported pytest wrappers also passed. No reference-assisted fallback was needed for these two actual repairs.

V5.4 also adds a shared two-attempt AI correction limit, a reference replacement preview, explicit confirmation before reference-assisted saving, clearer provenance in the browser and permanent boundary/control regression tests. These changes make a failed AI correction manageable and auditable. A model that remains wrong cannot keep making unattended requests or silently substitute a different scenario.

The complete deterministic suite passed **470/470 tests**, with zero failures and zero skips: 376 unit, 59 API and 35 real Chromium browser tests. All seven evaluator and five workflow defect seeds were detected. Separately, six newly authored local-model tasks improved from **4/6 correct raw drafts to 6/6 correct after focused correction**. These small engineering demonstrations establish the observed repairs, not universal AI correctness.

## Why the two expected values were wrong

For the first case, the written synthetic deductible is 10,000 cents. A 10,001-cent approved request therefore pays 10,001 minus 10,000, which is **1 cent**. The old AI expectation of 9,001 cents did not implement that deduction. This is a particularly useful regression because it distinguishes a tiny positive payout from zero and exposes an incorrect deduction immediately.

For the second case, 286,450 minus the 10,000 deductible leaves 276,450 cents. The synthetic per-evaluation payout cap is 200,000 cents, so payout is **200,000**. The old 186,450-cent answer was below the cap but did not follow the written calculation. A value being below the cap does not make it correct.

The new permanent tests include those exact wrong/right pairs and nearby values: 9,999 → 0; 10,000 → 0; 10,002 → 2; 209,999 → 199,999; and 210,001 → 200,000. These are literal authored answers, rather than expectations copied from an application response. The existing V5.3 reference-independence tests, boundary tests, denial rules and workflow checks continue to run.

## How focused AI correction now works

V5.3 appended a correction task to a long scenario-generation prompt. That prompt still contained instructions about creating new scenarios and a large set of contracts and fixtures. The model had enough information to correct itself but could still produce the wrong arithmetic. V5.4 gives correction its own shorter, focused prompt instead of carrying those scenario-generation instructions forward.

The correction request contains the frozen case, incorrect fields, exact per-step replacement expectations and the independent calculator's explanation. It explicitly distinguishes integer cents, zero, null payments, deductible subtraction and the cap. It asks the model to reproduce the reference-guided corrections without changing any scenario field. This is guided repair using supplied answers; it is not evidence that the model independently learned insurance mathematics or was fine-tuned.

The existing provider schema still fixes identifiers, titles, cited rules, rationale, assumptions, actors, actions and input data. The post-response comparison independently rejects a changed case or step order. New expected values are checked for structure, completeness and agreement with the reference. Providing the right answer in a prompt does not bypass validation.

Every request creates a separate child with `expectation_origin` set to `reference_guided_ai`, its parent identifier, correction root and attempt number. Raw model responses and the original cases remain available. Corrected drafts start unapproved. Editing, reviewing, running and exporting retain the existing hash, policy and reference checks.

## Why correction attempts are bounded across the whole history

Each correction history allows at most **two AI requests**. A button click initiates one request; the product does not automatically run a second attempt. The current usage is displayed in Studio. An exhausted history disables the correction button, and the server independently rejects another request before calling Ollama.

The budget applies to the original case and every correction branch. Reloading the page, restarting the service, selecting an earlier parent or creating a reference-assisted child does not reset it. Older V5.3 correction records count toward the limit. For each of the two retained failures, V5.3 had already used one correction; V5.4 used the second and final allowed AI attempt.

Failed provider calls, changed-scenario failures and interrupted jobs also consume an attempt. Their outcome may be unavailable, but the request was initiated and must not disappear from accounting. An interrupted correction retry therefore uses another available attempt; it cannot create an unlimited retry loophole. A reference-assisted preview remains available if the AI budget is exhausted.

The server derives usage from persisted correction children and checks it inside the same SQLite write transaction that creates the next child. This avoids trusting an in-memory or browser counter. A cross-service race test starts two requests on different branches with only one slot left and confirms that just one provider call is admitted. A separate test verifies failure plus interruption consumes both slots and another retry is blocked.

The limit is per correction history. Deliberately generating a brand-new experiment starts a new history; V5.4 does not claim an account-wide model quota or distributed service rate limiter. The lab remains a local teaching application.

## How the reference-assisted fallback works

A reviewer can click **Preview reference replacements** to inspect before/after expectation objects and the independent derivation for each changed step. Preview is read-only. It does not mutate a draft, contact Ollama, approve a case or execute a test.

Saving requires a reviewer label, a note and an explicit checkbox confirming inspection of the reference replacements. The request binds the experiment revision, reference fingerprint and preview hash. The server recomputes the preview before applying it. Editing a case, changing the calculator or submitting a different hash causes a stale-preview/revision rejection. The endpoint accepts no caller-supplied replacement case data.

The saved child is labeled `reviewer_confirmed_reference`, with `reference_assisted_of`, the calculator fingerprint and the inspected replacement snapshot. It has no raw AI generation for this operation. Its prompt/provenance explicitly records that no model request occurred. It is not counted as an AI repair, and it does not reset the AI budget. The parent retains its original cases and raw response, while its history records the child and previous approval, if any.

The child still requires a fresh selection, expectation attestation and review before execution or pytest export. Applying reference values is a correction action, not an approval. Reviewer labels are local attestations, not authenticated identities. The server does not claim a human personally inspected an operation just because a label was entered.

A failed or interrupted AI child can use its preserved frozen scenario for reference assistance. Unsupported reference scenarios, structurally invalid data and cases whose missing actions cannot be repaired by expectation replacement remain blocked. The fallback never invents setup steps or changes inputs to force a pass.

This fallback was exercised with explicit offline provider doubles in unit/API/browser tests, including two intentionally wrong AI answers followed by confirmation and execution. It was not used to obtain the successful actual-model results below.

## How to use V5.4 and what we achieved

Open AI Test Studio at `http://127.0.0.1:8895/#ai`. Generate a synthetic draft and inspect its completeness and independent reference result. Enter a reviewer label and correction note, then click the Ollama correction button if needed. The result is a separate draft with a parent link and attempt counter. If it is still wrong, another click can use the remaining attempt. No second request happens automatically.

To use the fallback, open the reference preview, inspect its before/after values and explanation, confirm the checkbox and save a reference-assisted draft. Inspect the source label so it is clear how the expectations were obtained. Then select the case, attest that its expectations were checked, save the review and run the approved snapshot. Confirmation of replacement alone never enables execution.

The repaired actual-model tests are available as `artifacts/v5.4/test_repaired_F03.py` and `test_repaired_F07.py`, with raw/approved snapshots and measurement results beside them. Run them together using `.venv/bin/python -m pytest artifacts/v5.4/test_repaired_F03.py artifacts/v5.4/test_repaired_F07.py -q`. Their saved engineering records use clearly labeled automated attestations, not authenticated human approvals.

We achieved both requested repairs, improved the demonstrated correction success, bounded the cost of repeated mistakes and supplied an auditable non-AI escape path. Incorrect drafts remain blocked. The reference still shares authored synthetic facts with the application, so a shared rule misunderstanding or a reference defect remains possible. This is a professional quality-engineering learning lab, not actual Medicare/commercial policy adjudication or compliance certification.
