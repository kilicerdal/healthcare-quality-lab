Healthcare Quality Lab V8.4 Engineering Report

Purpose and scope

V8.4 targets the failed V8.3 AI pilot and the intermittent WebKit coverage-evidence download. The intended outcome is a more disciplined model-only expected-value workflow and a download implementation that no longer depends on temporary browser Blob URLs. This report separates implemented engineering improvements from what actual models demonstrated.

Outcome: the known AI pilot now passes independent checks and actual HTTP through an explicitly resumed path, with no expected value changed. The coverage download uses a server attachment and passed repeated file-content checks across all three browsers. Final local and hosted standard suites passed 1,124/1,124 each; the full browser matrix passed 261/261 without retry. First-attempt model reliability and large-model latency remain unresolved.

The work is in the standalone project /Users/erdalkilic/Documents/Healthcare Quality Lab, on codex/v84-staged-ai-and-downloads. No VS Code session was opened. Existing projects and the unrelated V4 report draft are outside this change. All policies, member identities, claims, payments and benefits are synthetic. This is a research/showcase application, not real insurance adjudication or a Medicare compliance certification.

What failed before and why we changed the design

The original V8.3 small-model pilot was schema-valid but wrong. For rejected vision coverage it produced nonzero nominal deductible, copay and coinsurance-base worksheet fields. It copied policy limits into used deductible/OOP accounts. It also confused the noncovered amount with stored payment history and failed lifecycle counters. A zero payout alone was insufficient: every observation and worksheet still had to match independently.

The field-level diagnosis is retained in artifacts/v8.4/failure-diagnosis.json. The old raw answer is unchanged and still fails validation. Its failure is not removed from history or converted into a new pass.

One prompt previously asked a small model to solve coverage, cost sharing, account allocation, quote reuse, lifecycle counters and stored-ledger arithmetic together. V8.4 splits that output burden into two explicit stages. This is an engineering hypothesis about reliability, not proof that a different prompt makes a model correct.

Two recorded model stages

The new healthcare_quality/staged_expectations.py defines the staged protocol and StagedLab. First, the model emits pricing quotes: per-line worksheets and financial/account/policy values. The pricing instructions state that all rejected-line cost-sharing worksheet fields are zero, that used accounts are not limits and that rejected-only fresh accounts remain zero.

Second, a separate model call predicts step identities, quote references, ledger worksheets, HTTP status, state, revision, event count, ledger balance and ledger-entry count. It receives immutable inputs, raw synthetic facts and the first call's own unverified quotes. Its instructions distinguish submit from payment, increment revision/event counters on mutations and retain ledger entries even for a zero payment.

Assembly copies the model's quotes and lifecycle fields into the existing compact answer. It does not calculate expected money, overwrite wrong answers, choose correct quote values or supply reference corrections. Independent pricing, lifecycle and ledger checks run afterward. The original and optional blind-review predictions remain separately scored. No calculator output, evaluator mismatch or SUT response is fed into generation.

Both actual calls retain their prompts, schemas, hashes, responses, timing and generation-phase labels. A whole-case prediction now has two requests; optional review has two more; stepwise mode has two per step. The existing twenty-four-request ceiling and admission-time job budget apply to the expanded request count. Estimates include that multiplier. Older V8.2/V8.3 routes and stores keep their existing protocol instead of silently adopting a new one.

The V8.4 API is /api/advanced/expectations-v84, with a separate expectations-v84.sqlite store and readiness check. The workbench uses this endpoint and explains the two calls. Eligible current-source export remains an unapproved proposal; approval and actual HTTP execution remain separate. An interrupted record cannot become exportable merely because some pricing fields were completed.

Durable interruption across stages

The existing admission-time budget starts after separately bounded provider preflight. Per-call transport timeouts are clipped to remaining job time. If the lifecycle stage stalls after pricing succeeds, the record retains pricing, marks the running call interrupted and leaves later work unattempted. Late lifecycle output is fenced, and the generation lock remains held until its worker returns. Backend cancellation is best effort rather than an instant guarantee that Ollama stops computation.

A new regression deliberately blocks the second stage and verifies the completed pricing response survives, the visible job returns interrupted, no independent pass is manufactured and the lock is released only after the blocked worker returns. Other new tests exercise schema failure, exact copying of wrong numeric values, evaluator timing, expanded request budgets, API export and readiness.

Replacing the WebKit download mechanism

The first V8.3 complete browser matrix passed 260/261 checks, with one older WebKit coverage download timing out. A local recheck and an unchanged-source hosted rerun passed. That history established intermittency; it did not establish a browser root cause. V8.4 does not retroactively call it a proven Blob cleanup bug.

The old coverage button created a Blob URL, clicked a detached anchor and revoked the URL later. The new button points an attached anchor at a server download endpoint. /api/coverage/records/<id>/download returns the selected record as a JSON attachment with a stable filename, application/json content type, private/no-store caching and nosniff. The same coverage service supplies the read and download records, including current-source/approval validity markers. Authentication and role checks remain under the existing coverage API policy.

This removes Blob creation, revocation and URL-lifetime behavior from this feature. It is a concrete replacement of the suspect mechanism; it is not proof that every possible browser download failure is impossible.

The browser regression replaces URL.createObjectURL with a function that throws, then downloads the JSON three consecutive times, checks the filename and parses each file. Every parsed record must equal the authenticated record endpoint. This demonstrates real file delivery and contents rather than just the existence of a click handler. The API regression checks attachment headers, exact JSON and missing-record rejection.

The direct local check passed in Chromium and WebKit. Local Firefox could not launch because its installed runtime reported a profile-folder error, including when using a direct temporary directory. That is recorded as an environment limitation; Firefox acceptance is taken from hosted Linux CI rather than relabeling the local launch error as a pass. An early version of the fault-injection test returned the assigned function to Playwright, which caused Playwright itself to invoke it; the test was corrected to return nothing before acceptance.

Bounded actual AI evaluation

Before any new inference, evaluation-plan.json froze three tasks, models, budgets and the comparison condition. D83-01 retains the exact failed pilot inputs. H84-01 changes the rejected vision amount; H84-02 changes an exposed hospital scenario's amount. The latter two are fresh numeric input variants, not broad new scenario families or a ten-input qualification set.

The small-model job has a ninety-second admitted budget. It makes at most six calls for three first-attempt cases with no self-review. Only if it completes with fewer than three eligible cases does the installed larger model run the same tasks, with a 180-second budget. An interrupted small job would skip comparison to avoid overlapping backend work. The maximum is twelve calls and 270 admitted seconds, with preflight separate. There are no retries, post-result prompt adjustments or reference-assisted repairs in this comparison.

The small model, qwen2.5-coder:3b, completed all three cases in approximately 41.15 seconds. All three were schema-valid, but zero were strictly eligible: both observations and worksheets failed. The response median was approximately 6.12 seconds. Splitting the task did not fix this model's expected values on this sample. Its six raw calls and all failed values remain in small-model.json.

The initial qwen3.5:27b comparison reached its 180-second budget. It made three calls: two completed the original pilot, whose API/lifecycle observations were correct but whose member-before-OOP and capped-member worksheet values were wrong; the next fresh case timed out during pricing. Only one of three trials was assessed, zero eligible; two were unassessed. No completed accuracy percentage is claimed. The original comparison consumed nine actual calls overall and remains unchanged.

Development confirmation and explicit continuation

Inspection found that separating the pricing rules had omitted V8.3's explicit rejected-line member-before-OOP/capped-member checklist. That generic checklist was restored; it supplies rules, not a reference answer. Invalid phase envelopes were also tightened: a complete legacy wire answer cannot bypass an isolated pricing or lifecycle schema. Regression tests cover both bypass attempts.

A separately planned known-case confirmation then allowed two calls and 180 admitted seconds. It was not pooled with the frozen comparison and did not rerun the fresh cases. Its pricing call produced the correct complete financial quote and worksheet; lifecycle timed out at the job limit. This interrupted first attempt remains unassessed and nonexportable. The pricing-only diagnostic is explicitly not a complete AI-test pass.

One final, explicitly recorded lifecycle continuation reused the exact frozen model pricing and repeated only the unfinished lifecycle prompt/schema, after verifying source identity and installed model digest. It supplied no reference values, evaluator mismatches or edited expected fields. This was a disclosed retry of the unfinished stage, not a new first-attempt success. It completed in approximately 85.68 seconds.

The continuation produced correct lifecycle values but initially failed the old compact parser's unused-quote rule. Pricing had emitted Q01, Q02 and Q03 with identical complete worksheets and values; lifecycle correctly referenced Q01 for all three steps. No expected value was missing or numerically wrong. The strict parser nevertheless rejected unused Q02/Q03.

Exact alias normalization without value repair

V8.4 protocol version 2 adds a narrow structural normalization. It validates the full raw schema, rejects duplicate quote IDs and missing references, and removes an unused alias only if its entire worksheet and values exactly match a referenced quote. Canonical JSON comparison preserves numeric representation rather than coercing types. Any different amount or worksheet, or an undefined referenced ID, is still rejected.

This does not calculate an answer, select among conflicting predictions, rewrite a reference ID or correct a numeric field. All raw quotes remain in the original evidence. The audit records that Q02/Q03 were unused identical aliases and that zero expected fields changed. Dedicated tests reject differing money, differing worksheets, missing references and duplicate IDs. A fingerprinted fixture contains the frozen actual model wire output and proves complete independent validation succeeds without modifying it. Older V8.3 parsing retains its original contract.

The resumed output was revalidated under this explicitly different representation contract and then passed one actual HTTP case, covering submit, zero-payout payment and readback. Execution returned 409 while the proposal was unapproved. After an explicitly scripted engineering inspection—not independent human review—the actual HTTP run passed. All monetary, account, ledger and lifecycle expected values came unchanged from the model outputs. Zero reference-assisted numeric corrections were made.

This is a successful resumed known-case demonstration, not proof that the small model improved, that an uninterrupted first attempt passed or that fresh-input qualification succeeded. The original failed and interrupted records were not relabeled or overwritten. The continuation was a manual engineering procedure, not a new automatic resume/retry feature in the browser.

All twelve actual new model calls are accounted for: six small-model comparison calls, three initial larger-model calls, two confirmation calls and one lifecycle continuation. The original comparison's maximum admitted budget was 270 seconds; the explicitly documented confirmation and continuation added 180 and 120 seconds, respectively. Thus the broader development exercise had a 570-second admitted ceiling plus separate preflight. The extra stages are disclosed rather than concealed inside the original benchmark. No more model calls were made.

The successful evidence is in resumed-revalidation.json and resumed-http-execution.json; raw continuation and prior interruptions remain separate. The source that generated those model responses differs from the later exact-alias validator. Both identities and the raw-artifact hash are recorded. Scores under the changed parser are not presented as a matched before/after model-accuracy comparison.

How to use the result

Read docs/V8.4_GUIDE.md for startup, saved replay, explicit inference and evidence download. The showcase launcher preserves the existing state directory and seeds recorded evidence without generation. New V8.4 live trials use a separate store. The raw failed pilot remains available as a useful demonstration of why independent assertions and export gates matter.

The useful achievement is a narrower, auditable generation pipeline and a server-backed download with content checks. Model reliability is determined by retained actual results, not by the number of tools used, a passing offline fixture or a changed prompt. The original pilot now has a complete resumed model-authored case that passes actual HTTP without changed expected values. However, first-attempt reliability and larger-model latency remain unresolved. The small model failed the sample; the larger first attempts were wrong or interrupted. The fresh cases do not establish improved generalization. Those limits remain visible rather than described as flawless.
