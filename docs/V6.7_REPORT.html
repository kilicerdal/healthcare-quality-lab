Healthcare Quality Lab V6.7 Engineering Report

November 18, 2026 · Standalone project: /Users/erdalkilic/Documents/Healthcare Quality Lab

Why this version exists

Even correct local payment logic can fail when a separate service commits a payment but its acknowledgement is lost. Blind retries can duplicate money, and treating every timeout as failure can lose track of a successful external operation. V6.7 adds an actual external-service boundary to test those situations rather than simulating them only inside one function.

What we built

integration_peer.py is a separate synthetic eligibility/payment HTTP service with its own SQLite payment ledger. integration.py coordinates a local durable outbox and webhook inbox with the existing advanced claim store. integration_scenarios.py runs bounded scripted faults in fresh temporary stores. tools.integrations produces a source-linked receipt, and the engineering hub lets the user explicitly select an isolated rehearsal. Saved receipts use a new integrations-v67.sqlite store; no interactive claim is sent to a peer.

The peer recognizes synthetic member fixtures, validates exact payment fields, binds an idempotency key to the claim/amount and rejects changed-key input. A request may commit to its ledger and deliberately delay its response beyond the client timeout. Other profiles produce a transient 503, persistent timeout or incorrect receipt. The client uses only a fixed loopback peer, bounded response bodies and at most three delivery attempts per invocation. Redirects and arbitrary peer URLs are rejected.

How reconciliation works

Before sending money, the outbox freezes claim ID, member, amount, policy hash and revision. A database uniqueness constraint permits one payment intent per claim, including when different operation keys race concurrently. The coordinator verifies the claim snapshot before delivery and checks synthetic eligibility. Unknown outcomes remain pending. It queries the original key before retrying; a matching peer receipt can complete the original operation without sending another payment.

Only a receipt matching the frozen key, claim, integer amount and paid status can trigger local settlement. The local payment uses a deterministic idempotency key. An actual child worker exits after that local commit but before marking the outbox settled; a new coordinator instance reconciles the same peer receipt and replays the same local key. The test observes one peer payment, one local ledger entry and one payment history transition.

A changed claim before delivery is quarantined without creating an external payment. A wrong peer receipt quarantines the intent instead of marking a mismatched amount paid. An inactive eligibility fixture blocks delivery. A permanently ambiguous outcome stays pending and requires later explicit reconciliation; it is not falsely advertised as failed or settled.

Webhooks and concurrency

Webhook IDs are persisted with payload fingerprints. Identical replay is deduplicated; reusing the same ID with changed input is rejected. Older sequence numbers are retained as stale evidence without rolling back newer state. A webhook is a signal to reconcile, not independent authority to create a financial entry. Message payload quarantine is distinct from changing the payment's financial state.

The test set includes nine real HTTP scenarios, competing distinct-key intent creation, URL/redirect boundary checks, peer idempotency conflict and process-exit recovery. The UI and CI exercise these controls independently of any AI model. This is intentional: a model's availability should not determine whether core payment safety can be checked.

What we achieved and what remains bounded

Together, V6.3–V6.7 connect advanced AI proposals, independently checked expectations, explicit review, real execution, measured correction, local-model CI, presentable evidence and cross-service recovery. This integration demonstrates one initial synthetic payment per claim; it does not externally settle every later adjustment/refund. It is not a distributed transaction, production payment processor, general message broker or real eligibility feed. The report's final evidence appendix supplies measured results; it does not call the system flawless.
