# Healthcare Quality Lab V5.3 Engineering Report

## What we built and why

V5.3 adds an independent reference calculator and a deliberate, single-call Ollama correction step. Its purpose is to catch incorrect expected results before an AI-created test is approved, executed or exported. This addresses the specific weakness demonstrated in V5.2: all eight contemporary drafts contained their required business fields, but most still had incorrect expected results. A payout assertion can be present and still be wrong. Running that test against a correct application would produce a misleading failure.

The new flow is: written synthetic contracts → AI draft → structural validation → assertion completeness → independent reference comparison → optional AI correction → fresh reviewer approval → isolated execution. No application response is used to fill a test's expectations. The original model answer remains available even when correction succeeds.

The final local suite passed **441/441 tests**, with zero failures and zero skips: 349 unit, 58 API and 34 real Chromium browser tests. Seven evaluator and five workflow fault seeds were detected. The final eight-task live Ollama demonstration improved literal-answer passes from **3/8 original drafts to 6/8 corrected drafts**. The remaining two corrected drafts are preserved and blocked. These are small demonstration results, not a general model accuracy guarantee.

## How the independent calculator works

The reference module imports only standard-library modules: pathlib, copy, hashlib, json and re. It loads authored JSON facts for plans, rules, members, actors and workflow contracts itself. It imports no production evaluator, catalog service, workflow service, runner, Flask application or SQLite code. It makes no HTTP request and does not query the application's database. An automated import inspection enforces this dependency boundary; another test makes application evaluation and execution raise errors and confirms the reference calculation still works.

For financial calculations it uses a separate piecewise implementation. If the requested amount is at or below the synthetic deductible, the payout is zero. If the amount is at least deductible plus payout cap, the payout equals the cap. Otherwise, the payout is amount minus deductible. All money stays in integer cents. This differs from the production evaluator's clamp expression while implementing the same authored contract.

Literal examples checked independently in tests include 7,600 → 0; 10,000 → 0; 10,001 → 1; 100,000 → 90,000; 209,999 → 199,999; 210,000 → 200,000; and 278,900 → 200,000 cents. Invalid amounts such as booleans, zero, negatives, decimals, strings and amounts over the written limit produce an invalid-request observation, not a financial answer. Denial rules cover inactive policies, uncovered services, network requirements, authorization and formulary restrictions, with explicit precedence checks.

Workflow expectations come from a separate in-memory state machine. Each case starts empty. Submission calculates payout from the resolved member plan and creates revision/event 1 with no payment. Approval adds one revision and event. Payment adds one revision and event and sets the ledger amount to the stored reference payout. Reads and rejected operations do not mutate state. Ownership, duplicate claims and transition ordering are modeled explicitly.

Critically, that state comes from inputs and reference rules, not the draft's expected values. If the draft guesses a submitted payout of zero, the reference does not carry that guess forward into payment. It computes the real synthetic payout independently and retains that value through later steps. The comparison checks both JSON value and built-in type and identifies non-observable expectation fields.

Each result includes matched, mismatch or unsupported status; per-step reference observations; mismatch fields; proposed and reference values; and a plain calculation or workflow explanation. Completeness remains a separate check: matching the one field a model happened to include does not make an incomplete test approvable.

## How approval, execution and export changed

Studio generation, editing and detail views now expose structural validity, assertion completeness and reference agreement separately. In the browser, a wrong payout is displayed with the proposed value, reference value and calculation. Its approval checkbox is disabled. The server independently enforces the same rule, so bypassing the UI cannot approve it.

Approval records bind the reviewed case hashes, the assertion policy and the reference fingerprint. That fingerprint includes the reference implementation bytes, its version and the loaded authored facts. Changing reference logic or facts requires another review. A pre-V5.3 approval lacks this reference binding and cannot silently become a current approval. Existing raw generations, historical approvals and runs remain inspectable.

Execution and pytest export repeat the checks instead of trusting a previously rendered badge. Exported wrappers also check the reference fingerprint and case agreement at test time before invoking the runner. A changed or stale reference is therefore caught even after export. The unrestricted internal runner remains available for authored engineering tests and fault experiments; Studio's reviewed execution/export paths enforce the new gate.

## How the AI correction step works

The user explicitly clicks **Correct expectations with Ollama** after entering a reviewer label and note. The request includes the current revision. The server freezes the original case data and current independent calculations, then atomically creates a linked child experiment and records the correction request in the parent history. The parent revision advances and any previous approval is cleared; its prior approval is retained in the history event. Parent case data and raw model output remain unchanged.

One model call receives the frozen cases plus reference observations and derivations. Its JSON schema constrains identifiers, title, rationale, rules, assumptions, actors, actions and input data to their existing values. Only step expectation objects may change. A separate deep shape comparison checks the response after generation, including case and step order. The provider grammar and server check serve different purposes: even a provider that ignores the grammar cannot slip a changed scenario through.

The output is saved as an unapproved child. Correct values still require case selection, expectation attestation and a new review. A numerically wrong correction stays proposed and blocked. A changed scenario becomes a saved generation failure. Provider errors remain explicit failures. There is no silent backend replacement of expected values, no automatic approval, no automatic execution and no repeated model loop.

Correction uses the existing persistent operation leases, heartbeat and fenced completion. If its worker is interrupted, recovery preserves the child and frozen snapshot. An explicit retry retains the correction constraints instead of reverting to unconstrained scenario generation. A regression test expires the lease while inference is blocked, verifies late completion is refused, and verifies retry still rejects altered input data.

## What the live Ollama measurement showed

Eight tasks were authored and frozen before the final measurement: seven evaluator amounts around the deductible and cap, plus one four-step submission → approval → payment → read workflow. Literal answers were recorded before calls, separately from the calculator. Each original draft received at most one correction. No demonstration draft was automatically approved or executed; model calls used an isolated project-local store.

| Measurement | Original drafts | After one correction |
| --- | --- | --- |
| Structurally accepted | 8/8 | 8/8 |
| Required assertions complete | 8/8 | 8/8 |
| Independent reference agreement | 3/8 | 6/8 |
| Frozen literal task answer passes | 3/8 | 6/8 |

Correction repaired three of the five initially incorrect drafts, and preserved the three already correct answers. For the 8,300-cent task, the original claimed an 8,300-cent payout and correction produced zero. For the 210,000-cent cap boundary, correction produced 200,000. The workflow's corrected expectations included the 107,340-cent payout and payment together with the correct revisions and event counts.

Two final corrections remained wrong. For amount 10,001, the model returned payout 9,001 instead of 1. For amount 286,450, it returned 186,450 instead of the 200,000 cap. Both were detected without executing the application and remained ineligible for approval. These failures show why AI correction itself needs deterministic checking.

Two earlier pilot attempts are also retained. The first model corrected the money but renamed the case, which the shape guard rejected. A tuple-array schema then proved incompatible with the local provider, producing HTTP failures; the final compatible schema uses constrained item alternatives with the independent order/shape guard. Pilot measurements are kept separately and excluded from the final 8-pair table. Some final tasks had consequently been exposed during pilots; this is a development demonstration, not a fresh held-out benchmark or a blind causal estimate. No rejected answer was silently removed from its recorded run.

The final 16-request record contains frozen tasks, literal answers, settings, model identity/digest, prompt hashes, experiment identifiers, per-task outcomes and aggregate results. Individual proposal JSON files preserve prompts, raw provider envelopes, reference checks and lineage. Running the opt-in tool a second time refuses to overwrite an existing final measurement.

## How to use the new capability

Start the existing app and open AI Test Studio at `http://127.0.0.1:8895/#ai`. Generate a synthetic case, then inspect its assertion checklist and independent reference calculation. If expected values disagree, enter a reviewer label and note and click the explicit correction button. Inspect the new saved experiment, its raw answer and reference comparison. If the model still disagrees, manually correct the expectations or request another explicit correction; no automatic loop runs. Select only complete, reference-matching cases, attest that you checked them, save review and execute the reviewed snapshot in disposable state.

The references implement this lab's invented plan rules. They are not actual Medicare or commercial policy adjudication. Shared JSON facts, shared interpretation mistakes, missing scenarios and defects in the reference itself remain possible. The result is a stronger professional learning framework: observable AI mistakes, independent calculations, constrained correction, reviewer accountability, reproducible tests and preserved evidence. It does not establish real payer compliance or clinical/financial correctness.
