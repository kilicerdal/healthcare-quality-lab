# Healthcare Quality Lab V6.4 Engineering Report

November 18, 2026 · Standalone project: `/Users/erdalkilic/Documents/Healthcare Quality Lab`

## Why this version exists

A large number of generated tests is not evidence of quality. A model can produce syntactically valid cases with wrong expected values, omit payment/history assertions, duplicate earlier work or quietly change a difficult scenario into an easier one. V6.4 measures those failure modes explicitly and keeps reference assistance separate from raw performance.

## What we built

`advanced_evaluation.py` implements a frozen local measurement protocol; `tools.advanced_evaluate` is the explicit command-line entry point. Eight authored tasks are frozen in `advanced_cohort_v64.json` before inference. Two are development tasks and six are reserved until explicitly exposed. Each fixes the sequence, actors and business inputs. The model must supply the complete expected observations. A task that is easier, shorter or financially different cannot receive credit merely because its new answer is internally consistent.

The protocol stores cohort, schema/contract, source and prompt hashes, model identity/digest, fixed runtime settings, task selection, repeats and whether correction was enabled. Exposure is reserved atomically in the SQLite ledger before the first request. The first-exposure label means first recorded in that particular ledger; it does not prove that a public scenario was never seen by a model. Separate GitHub jobs use separate ledgers, so reports must not market each run as a new unseen holdout.

## Raw and assisted results

Every raw response remains unchanged. If explicitly requested, one additional model call receives the original output and independent feedback. Its result has a reference-assisted label, its own raw response and a separate eligibility count. Correction is not a deterministic replacement of model values disguised as an AI answer. It is another actual model request. Neither phase approves or executes application tests.

The workbench correction creates a new proposal linked to the original. It cannot mutate the original, reuse an approval or chain unlimited corrections. The scenario-preservation check is repeated at generation, review and execution. An adversarial test found a first implementation loophole where the later review recalculated only internal correctness; that was corrected before release. Replacing the original scenario with an easier correct case now remains blocked.

## Metrics and negative controls

The scorecard reports raw eligibility/schema validity, wrong or incomplete answers, provider errors, correction requests, assisted eligibility, latency and token use. Repeated task stability compares business observations rather than generated titles or case IDs. Repeats at a fixed temperature/seed are correlated; they are not independent population samples. Local token counts are reported without inventing an API dollar cost; no paid provider is called by this extension.

Positive controls pass the independent gate. Deliberate wrong payout, omitted ledger assertion, boolean money, unknown action, duplicate scenario, missing rejection readback, changed fixed input and non-JSON output controls are rejected. Provider failures are counted separately from financial wrong answers. Expired evaluation leases become interrupted while preserving partial rows and exposure history; late completion is fenced. Existing files cannot be silently overwritten.

For explicitly reviewed passing cases, the optional sensitivity score executes twelve named observable-contract mutants. This is distinct from the deeper pricing AST experiment already present. A score describes those known controls, not exhaustive defect coverage or proof that arbitrary generated tests are good. The final measurement appendix reports observed outcomes, including failures, without merging raw and assisted success.

## Outcome

The framework now supports a defensible answer to “did AI help?”: which exact inputs it received, what it actually proposed, what failed independent checks, whether one correction helped, and which reviewed assertions noticed bounded faults. The dashboard displays those distinctions rather than a single flattering test-generation count.
