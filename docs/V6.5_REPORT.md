# Healthcare Quality Lab V6.5 Engineering Report

November 18, 2026 · Standalone project: `/Users/erdalkilic/Documents/Healthcare Quality Lab`

## Why this version exists

V6.2 had an opt-in local-model workflow but no registered self-hosted runner. Ordinary hosted regression correctly used offline provider doubles, so a green workflow did not establish that local Ollama integration had run through GitHub Actions. V6.5 supplies an isolated, temporary route to exercise that missing boundary.

## How the runner is configured

`tools.ollama_ci` verifies the repository owner, current published main commit, clean source files, installed allowlisted model, bounded request plan and the dedicated Docker context. It refuses a different repository, unknown model/cohort, invalid repeats or more than twenty-four possible model calls including corrections. The only permitted cohorts map to fixed task IDs; user input is passed through structured subprocess arguments and workflow environment variables, not inserted as shell code.

The container image pins the official actions/runner 2.338.2 binaries for Linux arm64/x64 and verifies their release SHA-256 digests. It runs as a non-root user, drops capabilities, disables privilege escalation, mounts no host files or Docker socket, and registers for one ephemeral job. A unique unpredictable label targets the specific owner-dispatched workflow. The workflow requires this repository, the owner actor and main ref; it does not run on pull requests.

The local model remains on the existing Mac loopback Ollama service. A verified VM-to-host bridge and an internal relay present it as loopback inside the runner. This avoids opening a public model endpoint, downloading another model or installing a permanent runner service on the host. The isolated VM is a local validation tool, not a newly purchased cloud environment.

## Job and credential lifecycle

The launcher dispatches the bounded evaluation, identifies its job by the unique label, obtains a short-lived registration token into memory, and starts the container. Tokens are not printed or attached to release evidence. Runner diagnostics are kept in an ignored private log. The container processes one job and is removed. Cleanup also removes a matching leftover registration if necessary. The public receipt records the run URL, source commit, installed model digests, selected limits and whether the runner was removed, without containing registration credentials.

The live workflow installs only project-local runtime requirements and invokes the frozen advanced evaluator. It uploads raw and assisted measurement evidence. It never approves a draft, executes generated code or makes paid API requests. A successful job means that the bounded measurement completed and its evidence was retained; a model can still have zero eligible raw proposals. Those are separate outcomes on purpose.

## Repeat and operate safely

Use the dedicated Docker context and explicitly invoke `python -m tools.ollama_ci` from a reviewed, pushed checkout. The launcher checks main rather than executing an uncommitted local source tree. Local Ollama and the temporary VM must be available. The runner is deliberately absent when finished. Future on-demand live runs start it again; this delivery does not claim an always-on scheduled model service.

This isolation reduces the exposure of running a trusted public-repository workflow on a personal computer, but it is not a general untrusted-code sandbox or production multi-tenant runner platform. Review changes before launching a self-hosted job. The original legacy local-model workflow remains available separately and is not falsely reported as executed by the new advanced workflow.

## Outcome

The missing local-model/GitHub boundary is now configurable and measurable through a reproducible one-job lifecycle. The final receipt establishes the actual observed run and cleanup result. Hosted unit/API/browser CI remains independent of model availability.
